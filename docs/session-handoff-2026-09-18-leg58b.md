## 0. 一句话

**我们从世界书里拿到的，只是"ST 组装好的那一整段文本"的前 3 万字符**——
而 ST 那一段**怎么组装**（哪些条目进来、按什么顺序、谁被过滤）我们**只掌握了三条来源，没有掌握过滤与顺序**；
聊天 LLM 走的又是**另一条路**（ST 自己的注入器，`constant` 恒注入 + `selective` 关键词触发）。
⇒ **两条路的"生效集合"不同**，这正是"要通用解就得先搞懂它怎么生效"的原因。

## 1. 世界书是怎么写的（数据面）

ST 世界书 = `data/default-user/worlds/<书名>.json`，形状 `{ entries: { <uid>: entry } }`。
**三国.json 实测**（827 条 · 1,049,540 字符）：

| 字段 | 本书分布 | 语义（**ST 自己的**，非我们插件） |
|---|---|---|
| `disable` | `true` **563** / `false` 264 | 该条是否禁用 |
| `constant` | `true` **13** / `false` 814 | **恒注入**（不靠关键词，每轮都进上下文） |
| `selective` | `true` 814 / `false` **13** | **关键词触发**（靠 `key` 命中） |
| `vectorized` | 全 `false` | 是否走向量化 |
| `group` / `groupOverride` | 全空 / 全 false | 分组互斥（本书没用） |
| `key` | **827 条全为 `[]`** | 触发关键词（★本书为空，故 selective 靠 `keysecondary` 或前端机制） |

★**交叉表是干净的**（三批互斥）：`disable=true,constant=false` 563 · `disable=false,constant=true` **13** · `disable=false,constant=false` 251。

**恒注入的 13 条**（本题面，逐条）：
```
备用审查 · 音乐 · 演义说书 · 正史记载 · [mvu_update]变量更新规则 · 变量列表 ·
[mvu_update]变量输出格式 · 声誉 · 合理性及反魔改审查 · [mvu_update]变量输出格式强调 ·
剧本背景控制 · 经济指导 · 用户信息
```

★**这 13 条里没有历史正文**——`正史记载`/`演义说书` 是**输出格式契约**
（"触发时机=发生重大地缘政治变动时；输出必须用 `<history_record>` 包裹；示例=关羽樊城"），
**是书作者在教聊天 LLM 怎么写历史记录**，不是给它历史。⇒ **"聊天模型知道历史"不能由恒注入解释。**

★**两族的启用率都极低**：题名含「正史」221 条 → **启用 1**；含「演义」197 条 → **启用 1**。
⇒ 这 418 条角色条目**在磁盘上基本都是禁用的**（模式过滤的痕迹，见 §4 未知①）。

**条目的体例**（对写判据有用）：正文是**缩进的"字段：值"清单**，题名就是分类名——

```
【演义战力体系】
  战力分档体系:
    T0级_天下无双: 数值标定: 勇武 100   代表武将: 吕布（勇武100 / 统御75）
    T1级_超一流:   数值标定: 勇武 95-99
  属性联动机制:
    - 围剿规则: 若敌方统帅具备极高统御，可通过严密军阵将其困死
【[mvu_update]变量更新规则】  主角状态.属性.${勇武|韬略|内政|统御|气度|健康}: range: -100~100
【正史159】 / 【吕布正史】 / 【马超演义】 …   ← 角色条目，题名=角色名（数量最大的一族）
```
⇒ **体系条目与人物档案是同一个形状**（都是"字段：值"清单）——这是 leg58 的修法失败的直接原因（§5）。

## 2. 怎么生效（两套消费者，各走各的）

### ① 聊天 LLM ← **ST 自己的注入器**（我们不参与）
- `constant=true` 的 **13 条**：每轮恒进上下文。
- `selective=true` 的条目：由 **ST 按上下文扫关键词**命中后注入。
- ★**我们一行代码都没参与这条路**。⇒ 它"生效集合"的规则**在 ST 里**，不在本仓。

### ② 世界引擎 ← **我们收集的那段文本**（本仓唯一入口）
链路（逐跳核实过）：

```
web/index.js  collectWorldInfoEntries(ctx, character)        ← 收条目（三条来源 + 卡内置书）
   ├ src character?.world（卡上写的世界信息名）
   ├ chat  ctx.chatMetadata['world_info']（聊天级挂载；ST 的 assignLorebookToChat 写的）
   ├ glob  ctx.extensionSettings.world_info.globalSelect
   └ all   Object.keys(ctx.extensionSettings.world_info)
   ⇒ 逐个 ctx.loadWorldInfo(name) 取回；与卡内置书**按"键+正文"指纹去重**
        ↓
src/init-source.js  composeInitSource({character, worldInfoEntries})
   ├ collectEntries: 跳过 `disable===true || enabled===false`  ← ★**禁用在这一步被滤掉**
   ├ 每条渲染成 `【key】content`（key 取 e.key[0] ?? e.keys[0] ?? uid/name/comment）
   └ 剪枝序：世界书条目[全量] > 卡描述 > 场景 > 人格 > 开场白（预算 INIT_SOURCE_HARD_CEILING）
        ↓
src/abstract.js  extractWorldSetting
   ├ **小书（≤30000 字符）**：单发全量
   └ **大书**：`canonSrc = Array.from(src).slice(0, CANON_SRC_CHAR)` ← ★★**病在这**
```

★**关键事实**：`CANON_SRC_CHAR = 30000`（`abstract.js:44`），而三国那本组装后的 `src` = **198,135 字符**
⇒ 五件套**只读前 15.1%**（对全书 1,049,540 字符则是 **2.9%**）。

## 3. ★★ 病灶（真账实证，可复核）

⇒ 这是 **【声誉】条目**的十级（清名五级 + 恶名五级），**不是战力**。

1. **取样**（本棒已证）：五件套只读 `src` 的头 3 万字符 ⇒ 读到哪个体系**取决于它排在前面还是后面**。

   就算读到 `T0/T1 + 勇武 + 统御`，**多维也会被拍平**。

   所以第二层**要先问用户要什么**（"能如实记录多列" vs "引擎能拿去比谁强"——后者撞承重墙）。

## 5. ★ leg58 的修法为什么失败（**接它之前必须读**）

详见 `docs/measure-leg58-canon-sampling.md` §3。一句话：
`pickCanonSource`（体系条目优先、总量恒 = 30000、零 LLM 纯函数）在真书上**挑出来的是人物档案**。
三条原因：
1. **形态判据分不开「分类定义」与「分类的实例」**——人物档案的 `基本信息:/姓名:`
   与体系条目的 `核心属性:/范围:` **同形**（本书实测：264 条里 **220 条是 `<%_` JS 脚本条目**、
   31 条是人物档案、只有 **13 条**是"其它"）；
2. **"查找体系条目"这个思路依赖一个未验的前提**（体系条目在生效集合里）；
3. **单本调参＝过拟合**（用户明令"泛用化设计"）。

★**结论：不要急着接取样 heuristic**。先把 §4 的未知①③ 取证出来——
**"生效集合是什么"比"怎么挑"更根本**。

## 6. ★ 通用解法的**方法论**（用户点的那条路，本棒给出的骨架）

顺序不能反：

1. **先摸"书是怎么写的"**（§1）：字段语义、条目体例、体例分布（体系 vs 档案 vs 脚本）。
   ★本棒已经给了一份可复用的**量体脚本思路**：真书直读 + 纯函数，零模型调用。
2. **再摸"它怎么生效"**（§2 + §4）：**两条路**（聊天 LLM 的 ST 注入 / 引擎的收集+取样），
   各自的**生效集合**分别是什么、由谁决定。★这一步**必须用运行时取证**，磁盘字段不够。
3. **然后才谈"通用地抽取设定"**：只有知道了"生效集合里长什么样"，才谈得上
   "怎么在里面稳定地找到体系类条目"。★在此之前任何判据都是拿一本书猜。
4. **最后**才动结构（多维/单维）——而且**要先问用户要什么**（§3 第二层）。

★**一条可直接复用的判据来源**：条目的**体例**（`【题名】` + 缩进"字段：值"清单）是我们唯一
**与题材无关**的形态。体系条目与人物档案**同形**是难点；★可能的出路（**未验，留给下一任**）：
**"分类定义"的字段名是类别（`核心属性:`/`范围:`）、"分类实例"的字段名是实例（`姓名:`）**——
但这条我**只在一本书上试过，不许当结论**。
