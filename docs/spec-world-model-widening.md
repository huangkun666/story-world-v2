### 2.1 ★"没位置"那批怎么办（本节是用户追问后量到底的）

先把"没位置"拆开——**能不能由父级推出位置**：

| 位置分层（冷门池 603） | 个数 | 占比 |
|---|---|---|
| 明写位置 | **138** | 23% |
| **可由父级推出** | ★**0** | 0% |
| 无（父级也没位置） | **465** | 77% |

★**"可推"是 0** —— 因为父级自己也没位置（`太素帝 / 织命帝 / 渡虚帝 / 沉星帝 / 大虞` 全空着，
正是 leg25 f 记的那批空壳势力）。**位置继承这条路对这批人推不出任何东西。**

再把"除位置之外账上还有什么"分四层：

| 层 | 个数 | 处置 |
|---|---|---|
| ① 有位置（明写） | **138** | ★**上场**：每轮 1 条 ⇒ **可连供 138 轮**不撞名 |
| ② 无位置但**有归属**（父级在册） | **99** | 父级补上位置后**可推**（虞昭华、秦红袖…） |
| ③ 无位置无归属，但有分支/机构/实力等痕迹 | **290** | 位置补上再上 |
| ④ **只有名字与类别** | **76** | 见下（书里有、账上没有） |

**④ 那一批（万妖盟 / 幽都 / 无间魔宗 / 须弥山 / 阐教 / 天庭百官 / 蟠桃园 / 九霄龙渊宫…
势力 68 · 角色 8）——书里到底有没有？** 直接读世界书 `大荒-姬元真.json`（235 条条目，**纯只读、零模型成本**）：

| 读数 | 值 |
|---|---|
| 书里有条目/正文提到它们的 | **76/76** |
| 书里给了明确驻地表达式（`所在地:` 字段等） | **21/76** |
| 其中字段值**正好等于账上位置项** | ★**0** |
| 字段值不在账上位置集（⇒ 层级归一也救不了） | **12** |

| 切出多个（歧义 ⇒ 按"宁缺勿造"不猜） | **6** |

书里写的是**另一个粒度/层次**：

```
须弥山     ⇒ 第十三重天·太清境西方灵山区
九霄龙渊宫  ⇒ 第十六重天·碧落东海之巅
```

⇒ ★**结论（本候选的边界）**：**没位置的实体，不给它们派事——不编、也不偷偷归一。**
理由三条：①引擎"不发明事实"是红线；②位置线**已冻结**（START-HERE：「不可靠数据集 ⇒ 只呈现、不机制、
**不改集合/不补丁/不懒加载**」），补抽＝动位置集＝**撞冻结线，要用户单独点头**；
③"空着就是空着"是本仓四条不可越的线之一（§2 第 2 条）。

## 3. 三条候选（按"机械可核程度"排序）

### 候选乙 ★推荐：**账上处境锚**——让"有一处可去的人"自己上桌

**机制**：引擎每轮从账上选出**带真处境的冷门实体**（自池内 138 个有位置 / 212 个有归属者），
**按结构事实派生一条独立的 `state` 源事件根**，形如：

```
{"id":"ev_54_4","title":"〔昆仑道宫〕在西极昆仑山有所动作","source":{"type":"state"},"position":"西极昆仑山","ripples":["e_bk_1"]}
```

- ★**引擎不编故事**：标题里的三样——**谁 / 在哪 / 有动作**——全部是账上真有的字段
  （`entities[].name` / `entities[].location` / "`state` 源 = 由世界处境而生"这个既有语义），
  **不含任何新事实、不含数值、不含胜负**。叙事仍归模型（它有 `newEvents` / `newAgendas` 的创作权）。
- ★**它直接打在唯一被实测到的变宽机制上**：leg32 §5「事件**点名**新人 ⇒ 解除静默 ⇒ 他立起自己的线」
  （真账 `t24`「死煞异象惊动龙宫」⇒ 东海龙宫当轮立线）。本候选＝**把这个机制机械化、每轮稳定供给**。
- **门控不用改**：`state` 源事件天然不派生下游、按设计永不自动闭环（`entropy.js` 头注释），
  且它的 `ripples` 让被点名者获得"起头资格"（`gate.js` 第 3 条）。
- **代价**：一条事件 ≈ 93 字符 ≈ **28 est**；每轮 1–2 条 ⇒ **28–56 est/轮**（预算 0.2% 以下）。
- **风险与闸门**（三条必须写死，否则就是引擎编故事）：
  1. **只能用账上真有的 `location`**（值必须 ∈ `context.positions`）；没有位置的实体**不许编一个**（空着就是空着）；
  2. **每轮上限**（提案 1–2 条，报批）；且**同一实体 N 轮内不重复点名**（防刷屏）；
  3. **不与主线争位**：它进 `pendingEvents`，但**不改任何上限闸**（`AGENDA_CAPS` 一字节不动）。

### 候选丙（乙的轻量替代）：名单每人带一句账上处境

**机制**：`idleFaces` 的每一项**只加账上真有的字段**（`where` / `parent` / `branches` 计数），
**不编任何叙事**：`{"id":"e_bk_1","name":"昆仑道宫","kind":"faction","where":"西极昆仑山"}`。

- **代价实测**：N=12 ⇒ **178 est**（比裸名单只多 **9**）；N=36 ⇒ **536 est**（多 27）。**几乎免费。**
- ★**边界（红线）**：只递**处境字段**；`「昆仑道宫在西极昆仑山举办论道大会」`这种写法**是引擎编故事，不许**。
- **它比乙软**：乙是"引擎把一条事**摆上桌**"（机械可核：事件真的在账上）；丙只是"给模型一个理由"，
  ★**照 leg32 铁律 9 的教训，光喊没有机械判据 = 模型可以不听**。故丙**只能当乙的补充**，不能单独上。

### 候选甲（可选的前置一步，不是主线）：把主线那 8 条压成一链

**机制**：把"同一场大乱"的多节点**表示成一条链摘要行**（只留 id+标题，**id 全保**），
腾出 `pendingEvents` 里的重复位子。

- **代价/收益**：未决事件段 19 条合计 **1,769 字符 ≈ 529 est**，压掉重复节点约能腾 **~1,000 字符**。
- ★**但它只是"少看点重复"，不产生新事** ⇒ 与乙不同族。leg32 已警告过"单独限流主线"会截断真因果。
  **故建议：先上乙（+丙），甲留作后备**；不要单独用。
