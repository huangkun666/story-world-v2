## 1. 改动 1：抽取太慢 + 看不见（用户点单「你做吧」）

### 1.1 先实测（不脑内算——leg26 §4 的教训）

| 量 | 实测 | 取数方式 |
|---|---|---|
| 真源 | **235 条 / 265,866 字符** | `demo/match-source-fingerprint.js`（既有脚本） |
| 分块 | **213 行 / 5 块**，块大小 `[59215, 58673, 59892, 58902, 30344]`（**全贴 60k 上限的 97%**） | `demo/diag-leg25g-chunks.js`（既有脚本） |
| 调用数 | **1 次五件套 + 5 次名册 = 6 次**（小书 ≤30,000 字符则 1 次） | 读 `abstract.js:584` |

**初始化链路上只有抽取一处发模型调用**（`extractMove` 是纯正则、`composeInitSource`/`scanBookDeclarations`/`seedBookEntities`/`loadWorld` 全零 token）。

### 1.2 慢的三个真因（叠加）

1. **每次调用是重调用**：输出预算 `EXTRACTION_MAX_TOKENS=16,384`，且 `transport-http.js` 上方断留档实证 **reasoning 与输出共享该预算**；用户现场模型 `gemini-3.1-pro-preview`（推理型）⇒ **分钟级**。
2. **抽取超时蹭主调用**：`PROPOSED_CALL_LIMITS.timeoutMs = 120_000`，抽取侧未独立覆盖。
3. ★**超时被并进"瞬时错"**：`callOnce` 一律返回 `抽取调用失败: …` ⇒ `tryRosterChunk` 走 v1 的**拆半自适应**：
   超时 → 对半拆（每半再各 2 分钟）→ 拆到 `ROSTER_CHUNK_DEPTH=4` → 保底重试 ⇒ **单块最坏 1+2+4+8+16+1 = 31 次 × 120 秒 ≈ 62 分钟**，
   **而这 62 分钟之后结果仍是"跳过降级"**（纯烧时间不长数据）。
   ★**根因一句话**：拆半拆小的是**输入**，而超时主因是**生成时间**（输出预算每次固定 16,384）⇒ **这味药对超时无效**。

### 1.3 看不见的真因

`web/index.js` 只在开头 `setStatus` 一句；`diagExtract` 只在调用**返回之后**出声；`logInitDiagnostics` 只在**整件事结束**出声；`abstract.js` 块循环里**零日志**
⇒ 6 次调用是黑盒，**"正在跑"与"已经卡死"在界面上完全同形**。

### 1.4 三件改动

| # | 改了什么 | 落在哪 |
|---|---|---|
| **F2** 超时/重试分治 | `EXTRACTION_TIMEOUT_MS = 300_000`（**提案态**）+ `markTimeout()` 按"本控制器自己发过中止"打 `sw2Timeout` + `tryRosterChunk` **超时即止损跳过**（不拆半、不重试）；**拆半/保底重试只留给瞬时错**（那才是它的原始理由） | `transport-http.js` · `abstract.js` · `transport-config.js`（`extraction:true` 显式档） |
| **F1** 进度可见 | 注入式 `onProgress`（`{step,phase,index,count,chars,ms,ok,error}`，**抛错不影响抽取**）→ 状态栏「名册第 x/5 块」+ 控制台每段真实字符数/耗时 | `abstract.js`（`makeProgressLog`/`describeProgress`）· `web/index.js` |
| **F1b** 读秒心跳 | **1 秒心跳**按**真实已花时间**重写状态栏（旧法用"已完成段之和"⇒ 正在跑的那段不在里面 ⇒ **恒显 0 秒**，这就是用户说的「读秒没变」）+ 每 **30 秒**控制台一行"仍在跑" | `web/index.js`（`extractionProgressHandler`，**导出以便真测**：注入假计时器） |
| **F3** 失败显形 | 块跳过时写明**第几块/共几块/多少字符/什么原因**；成功文案带**实测调用数与秒数**；失败文案带耗时与"每段成败见控制台" | `abstract.js` · `web/index.js` |

**契约层未动**：`timing`/`progress` 只是返回值上的只读附加字段（不落盘、不进 schema）。

## 2. 改动 2：快照容错（新机制 · 先细案后施工）

用户令：「再做一个快照容错系统，**用户和 llm 每一步的修改都会生成快照**」；三问拍板：**①IDB 独立库 ②保留 15 步**（原话「30步要占很大内存吧，先用15步吧」）**③只回世界账**。
细案：`docs/spec-snapshot-fault-tolerance.md`（**§7 是实测读数与两条待决，接手先看那节**）。

### 2.1 为什么这么设计（全部有实测依据）

- 热账 `world` = **179,157 字节**（618 实体 / 751 名号）；聊天首行 **3,106,101 字节**；ST 保存语义 = **整份重写聊天**。
  ⇒ ★**一步一份完整快照塞热账会把首行撑爆**（15 份 = +2.5 MB，每步 `saveChat` 写放大 3 MB × 步数）⇒ 落 **IndexedDB**（与既有「旧卷」同层，键空间分开；**热账一个字节都不加**）。
- **锚点制**（本设计最重要的结构选择）：每 `ANCHOR_EVERY=5` 步一份 **full 锚点**，其余步落**相对锚点的 delta**
  ⇒ **修剪 = 从最旧直接丢**（丢锚则丢它名下 delta）⇒ **结构上不可能留断链**；恢复 = 锚 + 一个 delta **两步到位**。
- **唯一落账收口 `writeHotMeta`**（全仓 6 个调用点、9 处落账都走它）⇒ 一处收口全步覆盖；**fire-and-forget + try/catch + 写串行** ⇒ **快照失败绝不影响世界推进**（同记忆投递纪律）。

### 2.2 实测成本（`demo/measure-snapshot-cost.js`，同容量合成世界 17 tick）

| | 值 |
|---|---|
| full（锚点） | 57,646 → 89,342 → 120,353 → 151,368 字节（**随世界增长**） |
| delta | 6,249 / 6,794 · 12,466 / 13,410 · 18,684 / 19,627 · 24,904 / 25,844 字节 |
| delta 均值 | **15,120 字节**（full 均值的 1/7） |
| 17 份总占用 | **600.9 KB**；15 份窗口 **480.4 KB** |

★**delta 随距锚步数线性增长**——这是锚点制的**有意代价**（见 §5 待决 A）。

## 3. 我方的错（如实留档，这一棒错得最多）

1. ★**「超时机制失效」这个判断是错的**：我曾怀疑 `abort(reason)` 传 non-cloneable 会抛 ⇒ 超时没生效。
   **本机实测证伪**（`abort(new Error)` 正常返回、`signal.aborted=true`、挂住的 fetch **528 ms 被中断**）⇒ 超时本来就生效，**别再去修这一处**。
2. ★★**「提到模块顶层 ✓」是假绿（最严重的一次）**：我用**行首缩进**当判据，而 `trimStart()` 对**未闭合的模板字符串行**也给 0
   ⇒ 我报"已修复"，用户**第二次**撞上同一条 `落账失败：pushMemoryNow is not defined`。
   **教训：判据要经得起"能不能认出坏形状"的自检**（现在那条锁自带自检：喂一个块内声明样本，必须被认成 depth=1）。
3. ★**进度指示器只做事件驱动**（用户「读秒没变」→「段也不变」）：一次调用几分钟里页面结构上无可变。
   我把"看不见进度"改成了"**看不见在动**"——**"读秒在跳"才是"它没死"的唯一证据**。
4. ★**快照 `seq` 只活在内存**（刷新即归零 ⇒ 新链按 id **覆盖**旧链，用户看到"一下子多了这么多"且重复份永远清不掉）。
5. ★**「落账」不等于「世界动了」**：我把快照挂在 `writeHotMeta` 上，而它在"账本逐字节没变"时也会被调用 ⇒ 对同一份世界反复拍（一屏 11 份 0KB、tick 全是"第 0 轮"）。
6. ★**「下拉自己关」我一开始判成观感问题**，实际是 `set-param` 整页重绘**销毁了正在展开的 `<select>`**。
7. ★**测试夹具与真实用法不一致**：进度锁第一版传空 `events` 数组（真实路径由外层累积）⇒ 锁报红而产品代码没错；
   快照夹具用 `structuredClone`（保留 `undefined` 自有键）而真账走 JSON（**不可能有**）⇒ 造出假分歧。
8. **`applyDelta` 六个真 bug**（全部实测抓到、全部由判据锁死）：数组删除用 `splice` 挪位 / 深拷"合并自己那张表" / **漏传两个 delta 表 ⇒ 退化成浅拷 ⇒ 就地改写调用方的世界** / 序号解析静默降级成 0 / 锚点间隔按 **tick 差**算 / **delta 相对上一步算**（症状：**delta 份全错、full 份全对**）。
9. **固定取样窗口的锁**：多条锁用 `slice(a, a+1600)` 这类魔数，代码一长就**假红**（改注释都会触发）。
10. **`_tmp-move-scope.js` 临时脚本**用完已删（不留垃圾）。
