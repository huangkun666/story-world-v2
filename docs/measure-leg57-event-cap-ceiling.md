## 2. ★★ 三条结论（按重要性）

### ① 输出天花板**没有**咬到：截断从未发生
`finish_reason` **13/13 = `stop`**（`length` 一次都没有）。completion 峰值 2199 token ＝ 上限的 **13%**。
⇒ ★**leg54 写在页上的那句话是成立的**：「填得很大**不会凭空多出事情**，超出它一次能写的量时，
你不会看到"被拦"，只会看到这一轮没长出新事」——而且实测**连"被拦"都没出现**（拒签 0 次），
因为模型压根没写到那个量。**页上那句不是空承诺。**

### ② 上限不咬，因为它**远高于模型的自然产量**
模型自然写 **3–11 件/轮**。`每轮事件` 从 12 → 30 → 50，**落账件数没有单调上升**
（ev30 三轮 5/11/9 · ev50 三轮 10/5/4）⇒ **那一格确实是一张纸**。
★与 leg54 的推算**方向一致、量级不同**：它推"够写几十条"，实测是**模型自己只肯写个位数**。

### ③ ★**真正拉动产量的是「每轮递线」，不是「每轮事件」**（本棒的新读数）
对照臂（`每轮事件=12` 不变、只把 `每轮递线` 10 → 3）：落账 **11 → 5 / 5 / 5**（三轮**稳定 5**）。
⇒ **给模型几条线要走，它就写几件事**——产量由**输入侧**的线捆条数决定。
★这条**必须说清一处不可比**：leg40b 记档「59 轮真账逐轮新事件 max 4」是在**别的环境**下量的（`递线` 默认 3），
与本棒"递线=3 ⇒ 5 件"同量级但**不完全同值**（采样随机性 + 世界状态不同）⇒ **不能把差异记成某个变量的功劳**。

## 3. ★ 一条**没被验到**的路径（如实登记，别当成已验）

`eventCapWarnings` 全程 **0** ⇒ **"事件洪峰拒签"那条路本轮一次都没走到过**：
模型从没提议超过上限 ⇒ `settle.js` 那个"按提议序保留前 ≤N、超出拒建并留痕"的闸**没被执行过**。
⇒ 所以 leg54 页上那句"**不会有报错**"（拒签是静默的、tick 照常前进）**本棒没能验到**——
它要**模型真写出超上限的提议**才会触发。★要验它得换法子（例如 `每轮递线` 拉到 30 逼产量，
或直接在副本上喂一份超量 step），**本棒没做**。

## 4. 纪律核对

- **真账**：9.2 MB，mtime `2026-09-14 16:40` **未变**（跑前跑后逐项一致）✓
- **生产仓库零改动**：`src/` `web/` 本棒一行未动（`git status` 里那几个改动全是 leg56 的）✓
- **同参自证**：装置打印生产 transport 的**实发参数** —— `{"model":"gemini-3.1-pro-preview","max_tokens":16384,"temperature":0.7,"response_format":"json_object"}` ⇒ 与 `transport-http.js` 逐项相同 ✓
- ★**装置自身的两个 bug 都当场被抓出**（留档）：
  ① `installFetchSpy()` 原先在 `resolveWorldTransport()` **之后**调用 —— 而 `createHttpTransport` 的
     缺省参 `fetchImpl = fetch` **在创建那一刻就绑定**了 ⇒ 代理永不被调用（症状：`finish=null` 而 tick 照常成功 =
     **装置静默失灵**）⇒ 修成"**先装代理、后建 transport**"，并加"读不到就显式喊装置失灵"的自证；
  ② `r.stage.step.newEvents` 恒 `null` —— `stage` 的形状是 `{chronicle, warnings, events}`，**不含 step**
     （第一版提议数永远是 null，被自证打出来发现）⇒ 改成从 `stage.events` + 洪峰拒签痕反推。
