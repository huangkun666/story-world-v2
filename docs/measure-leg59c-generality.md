## 4. ★★ 泛用化设计（定稿形状：**一次探测 → 一张路由表 → 三档读法**）

### 4.1 探测（纯函数 · 零模型 · 零 JS 执行 · 可判据锁）
```
输入：本书的启用条目（已经过「先按『键+正文』去重、再跳 disable」两步 —— ★顺序不许反）
输出：{
  kind:        'shell' | 'plain'，
  constDecl:   [{title, chars}]   ← 恒注入壳声明的目录（每轮必读）
  keyShells:   [{name, keys, decls}] ← 靠 key 命中的壳
  titleSeries: [{affix, kind:'pre'|'suf', count, members}]
  windowCover: {entries, chars}   ← 旧口径头 30000 覆盖了多少
  srcChars, enabledCount
}
```

### 4.2 路由表（★每一格都有实测支撑，没有一格是猜的）

| 型 | 判据 | 读法 | 本棒实测落在这一格的书 |
|---|---|---|---|
| **A** | `srcChars ≤ 30000` | **全读**（现状就对，零改动） | Eldoria · Global · 实教世界书 |
| **B+** | 有恒注入壳 **且** 声明命中 > 0 | **① 恒壳声明的目录全读**（这是"必读档"）；② key 壳的声明按命中取 | **三国（28 标题/50,190 字）** · **大荒（7 标题/1,673 字）** |
| **B** | 有壳、恒壳不声明，但 key 壳有声明 | 按 key 命中取声明；无命中则退 `windowCover` | （本轮 9 部里没有纯 B） |
| **C** | 有壳但声明全部落空（引用的标题不在启用集里） | 声明**当线索不当命令**（可能引用被禁用的条目 ⇒ 只能靠题名系列 + 预算分级） | （本轮没有） |
| **D** | **无壳** 且 `srcChars > 30000` | **题名系列分类 + 预算分级**（见 4.3）；`windowCover` 只作兜底 | re0（系列 81%）· 实教卡（86%）· 综漫（58%） |

### 4.3 D 型的读法（诚实版：这是**降级方案**，不是等价方案）
1. **题名系列给类别**：`人物-×55` / `考试-×10` / `制度-×7` ⇒ 引擎知道这本书里"有哪些类的东西"；
2. **类别内按 key 命中/角色上场取**（引擎已有这条通道：`pack.js` 的分栏就是干这个的）；
3. **没有 key 的类别** ⇒ 按系列**轮转抽样**（`idleFaces` 那套轮转思路，本书已经在用）；
4. ★**明说做不到的**：D 型书里**"整本书只有一个大类、且没有 key"**的情形（如 `综漫-春物` 12 条覆盖全类型、1.03M 字）
   —— 任何"按位置"或"按题名"的策略都抽不出"体系"，**只能靠"用得上时再检索"**（把料存下来、按需查），
   **那是另一个产品决定，需要报批**。

## 7. ★★★ 追加（leg59d）：**"世界设定必须抽象吗？"——代码层的答案**

> 用户追问：「**世界设定是必须要抽象的吧？**」⇒ 我去代码里把"谁在消费那五件套"逐处查了一遍。
> 结论：**名册必须抽象；另外四件**（`rules`/`society`/`techOrMagic`/`historyNotes`）**抽象了但没人用**——
> 而且**抽完就把原文删了**（`sourceText` 是个从来没写过的字段）。

### 7.1 逐字段的消费面（全仓 grep，含 src/web/test/demo）

| 字段 | 引擎真用？ | 模型看得见？ | 消费处 |
|---|---|---|---|
| **`bookEntities`（名册）** | ★**是，承重** | 只以"入账实体"形式 | `abstract.js` 入账/归属反推/类别（1442/1142/1461…）· `check-step.js:218` 来源三型命中 · `entity-lookup.js:150` · `render` |
| **`powerScale`（力量谱系）** | ★半用 | ✗ | `abstract.js:1434` 当**档位标签校验词**；其余只在 `render.js:1603-1628` 显示 |
| `rules`（法则） | ✗ **显示** | ✗ | 只在 `render.js:1604/1626` |
| `society`（社会格局） | ✗ **显示** | ✗ | 只在 `render.js:1627`（**真账里 52 字**） |
| `techOrMagic`（力量体系） | ✗ **显示** | ✗ | 只在 `render.js:1627`（**真账里 94 字**） |
| `historyNotes`（史略） | ✗ **显示** | ✗ | 只在 `render.js:1605/1628` |
| `situation`（世情句） | ✗ **显示** | ✗ | `render.js:287/715`（真账 24 字） |
| **原文 `sourceText`** | ★**不存在** | ✗ | `abstract.js:1308/1356` 读它——**但没有任何一处写过它** ⇒ 两处**死代码** |

★并核了一件事：`pack.js` 有一条明写的体积纪律——**"冻结层不入包"**（`pack.js:424`）⇒
**模型每轮看不到 `powerScale`/`rules`/`society`/`techOrMagic`/`historyNotes` 里的**任何一个字。
⇒ 那四件套目前是**纯展示层数据**（"设定档案页"上的四张卡片）。

### 7.2 由此得到的结论（不是"要不要抽象"，而是"哪些必须抽象、哪些必须留原文"）

1. **必须先抽象的是"账本需要拿它当索引用"的那些**：名册（名号 + 类别）。
   理由：账上每次行动/事件/归属都要写实体名，模型每轮都得看到——**这部分必须是"短表"**，
   而且 ID 分配必须确定 ⇒ **非抽不可**。
2. **剩下的三件（社会格局/力量体系/史略）压成 52 字 / 94 字 / 2 条，等于什么都没说**——
   它们既进不了包、也不进任何判断 ⇒ **抽象它们纯是白付一次调用**。
3. **"抽完就删原文"是这套设计真正的病**：抽取是**单向门**，账本里那 52 字是**唯一副本**。
   引擎想查什么，**无处可查**（`sourceText` 是死字段）。
4. ⇒ **定稿口径（提案，未实施）**：
   **甲、选择性抽象**（只抽象"必须能精确判等"的东西：名册条目 + 档位表；其余一律不抽）；
   **乙、留原文**（`canon` 里补一个压缩过的 `sourceText` / 只存条目索引 + 指纹）；
   **丙、要用时现查**（对齐 ST 那一侧的做法——`getwi` 就是"要用时才取",而它是**一轮内完成**的）。
   ★甲的"档位表"明确一点：**要抽就得全抽**（三国那本该抽的是 `演义战力体系`，
   抽成 `[{level,note}]` 没问题——**问题从来不是抽象，是抽象错了对象**）。
5. ★**被删掉的代价是可见的**：若当初留了原文，本棒 §1 那 33,555 字的缺口、`powerScale` 拿到"声誉"这件事，
   都能在**账内**直接对账；现在只能去翻 ST 的磁盘文件。

## 8. ★★★ 追加（leg59f）：**聊天 LLM 是怎么知道"何时该有哪条设定"的**（装置读数）

> 用户追问：「**聊天 LLM 肯定不是全量注入**」——**对**。实测它的机制是**两套触发并集**，
> 而且**两套都是"在组装那一刻定下来"，不需要模型去搜、不需要向量、不需要额外调用**：

### 8.1 第一套：**关键词触发（作者给每条写了 `key`）**
| 量 | 三国实测 |
|---|---|
| 启用条目 | 264 条 |
| **带触发词（`key` 非空）** | **249 条** |
| 触发词总数（去重） | **655 个**（平均每条 2.9 个） |
| 无 key 又非恒注入 ⇒ ST 永远跳过 | **2 条**（544 字） |
| **头 30000 里带触发词的** | **3 条** ★ |

⇒ **这本书的"何时取哪条"几乎全写在 `key` 字段里**（ST-Prompt-Template 官方口径：
`key` = 触发词，命中即注入）。**旧窗口恰好把带触发词的条目挡掉了 99%**（3/249）。

### 8.2 第二套：**作者写的条件表达式**（模板层，不含关键词）
220 条模板的触发条件分布实测：**模式分支 187 条 · 年份段 33 条 · 好感度/变量 0 条**。
⇒ 它是**确定性条件**（`route==='正史'` / `currentYear>=159&&<168`），求值即出结果。

### 8.3 ★★★ 决定性读数：**把这套扫法搬到引擎侧，用账上的名字当扫描词**
| 扫描文本 | 命中 keyed 条目 | 命中率 | 命中条目正文量 |
|---|---|---|---|
| 只扫**账上实体名**（85 个） | 88 / 249 | 35% | 115,492 字 |
| 只扫**盘算+事件涉及的名字** | 48 / 249 | 19% | 64,334 字 |
| **只扫"最近聊天原文"（= ST 自己的做法）** | **45 / 249** | **18%** | **12,437 字** |
| **三条并集** | **119 / 249** | **48%** | — |
| （对照）旧口径：头 30000 | **3 / 249** | **1.2%** | — |

★**也就是说**：**引擎账上现成就有 85 个权威实体名 + 在飞盘算 + 事件 + 上一轮自己写的叙述**，
拿它们当扫描词跑一次 `key` 匹配（纯函数、零 token、零调用），
**能命中近一半的"该读条目"——而现在的头 30000 只命中 1.2%。**
★注意命中的**正文量差别很大**（12k vs 115k）：扫聊天原文命中少但精（12,437 字 ≈ 一次调用装得下），
扫全部实体名命中多但会爆预算 ⇒ **"触发"只是候选集，仍要按预算取前几条**——这与 ST 自己的 `budget` 同款。

### 8.4 ⇒ 口径修正（接 §7）

> **"何时能有对应的设定"这件事，书里已经写好了两遍**：
> ① **`key` 触发词**（249 条）② **作者的 `<% if %>` 条件**（年份/模式）。

⇒ 聊天 LLM 靠"**扫上下文命中 key + 求值模板条件**"决定注入什么，**决定权在作者、不在模型**。
⇒ 引擎一直用的是第三种东西——**"按书序读前 3 万字"**，**它跟"该不该读"完全无关**。
⇒ **正解不是"换一种更好的摘要"，也不是"向量检索"，而是"读同一个触发面"**：
**引擎在第 N 轮把"本回合包里的名字 + 上一轮叙述"当扫描文本，跑一次 `key` 匹配，
取命中条目的正文现算**——这正是 §7 说的"要用时现查"，
而且**与 ST 两侧同一条判据**（key + 条件），不需要新的机制、不需要模型参与。

★**如实登记的两条**：
1. **触发词的质量是作者给的**：本书 655 个词里有「师」这种极短词（可能是噪音，会误命中）；
2. **本轮没有真机读数**：命中的条目**模型会不会照它写**、注入量对生成质量的影响——**要真跑几轮才敢说**。
