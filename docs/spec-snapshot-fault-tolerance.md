## 0. 一句话

**每一步落账都拍一份"可回到的完整世界状态"，坏账能退回来。**

## 3. 设计（提案）

### 3.1 数据形状（纯函数，可 Node 测）

```
快照记录 Snapshot = {
  id, tick, at,                        // 时点
  reason,                              // 'pre'|'post'  + 触发名（tick/查书/批量/初始化/导入/清演化层）
  kind: 'full' | 'delta',
  baseId,                              // delta 的基线（上一份）
  set / del,                           // delta：字段级 路径 → 新值 / 删除的路径
  msgIndex,                            // 当时的聊天消息下标（供"连对话一起回退"用）
  bytes,                               // 自身体积（用于配额淘汰）
}
```

- **full**：整份 `world`（166 KB）——只在**基线点**写：初始化、导入、每 N 步（N 待定）。
- **delta**：与上一份的**字段级差异**（纯函数 `diffWorld(prev, next)`）。一步的真实改动量级：一个 tick 改几十个字段 ⇒ 量级 **KB 以下**（实施时实测确认，不预吹）。
- **判据**：`applyDelta(base, delta) === next` 逐字节相等（往返锁）；`diffWorld` 必须**确定性**（同输入两次逐字节一致）。

### 3.2 存储

- **新 IDB 库**（与旧卷分开，别混键空间）：`createIdbSnapshotStore(chatId)` → 照 `idb-backend.js` 的形状。
- **保留策略**：滚动窗口 `{最多 N 份 or 最旧 M 步 or 总字节上限}`，超限**从最旧淘汰**（淘汰前先把"被淘汰的 delta 的基线"合并成一份 full，避免链断）。
- **链完整性**：恢复需要 `full + 其后所有 delta`；任何一份缺失 ⇒ **该链标记不可恢复**（如实报，绝不"大概恢复"）。
- **热账只加一个指针**：`snapshotSeq`（最新 id）——**不动 `world` 形状**（契约层零改动）。

### 3.3 触发点（"用户和 LLM 每一步"）

| 时机 | 触发名 | 说明 |
|---|---|---|
| `writeHotMeta` 落账前 | `pre:<原因>` | **改动前**的状态 ⇒ 这就是"回到上一步"的锚 |
| `writeHotMeta` 落账后 | `post:<原因>` | 改动后的状态（与下一份 pre 常equal，实施时按"内容相同则不写"去重） |
| 每 tick 结束（`save` 回调） | `tick:<n>` | 一句话可读的里程碑（用户在界面上按 tick 认） |
| 初始化 / 导入 / 清演化层 | `full` | 基线点（必须 full，否则链没有根） |

**同一步内的两次写**（`onPreStep` 查书 + tick 演化）各生成一份 ⇒ 用户看到的是"查书前/后、演化前/后"都能退。**这是提案，可收敛**（见 §5 Q2）。

### 3.4 失败语义（硬纪律，照本仓既有口径）

1. **快照写入失败绝不许影响世界推进**（照 leg26 记忆投递的"失败零阻塞"）：`try/catch` 吞掉，只进状态栏与控制台。
2. **不许"大概恢复"**：链断/字节不符/applyDelta 不闭合 ⇒ 明确报错并**原样不动**。
3. **恢复前先给当前状态拍一份 full**（防"恢复错了回不去"）——这是容错系统的自保条款。
4. **配额满**：先淘汰最旧，淘汰不动（窗口只剩 1 份）⇒ 如实报"快照已满，最旧不可退"，不静默丢。

### 3.5 界面（放哪待定，见 §5 Q3）

- **设置页**：一行状态「快照 37 份 · 覆盖第 21–58 步 · 1.8 MB · 最新 12:03:41」+ 一个列表（按 tick，带 `reason`）+ 「回到此步」+ 「清空快照」。
- **恢复一律二次确认**（不可逆动作），确认文案**写明会回到第几轮、会丢哪些步**（照本仓"文案是事实拼句"的纪律）。

## 7. ★实施后的真实读数与两条待决（**接手先看这一节**）

### 7.1 实测（`demo/measure-snapshot-cost.js`，同容量合成世界 618 实体，17 tick，`SWV2_CHAT` 指真账取容量）

| | 值 |
|---|---|
| full（锚点） | 57,646 → 89,342 → 120,353 → 151,368 字节（**随世界增长而涨**） |
| delta | 6,249 / 6,794 · 12,466 / 13,410 · 18,684 / 19,627 · 24,904 / 25,844 字节 |
| delta 均值 | **15,120 字节**（full 均值的 1/7） |
| 17 份总占用 | **600.9 KB** |
| 15 份窗口 | 480.4 KB |

★注意：这个合成世界在 17 tick 里**长了 3 倍**（`runSmoke` 的合成步骤每轮加实体/事件），
而**世界大小直接决定 full 的大小** ⇒ 上表是"世界会长"的口径，真账的稳态会长得慢得多。

### 7.2 ★待决 A：delta 不是平的，它**随距锚点步数线性增长**（设计取舍，请拍）

实测：delta 从 6.1 KB → 12.2 → 18.3 → 24.3 KB（锚点后第 1/2/3/4 步），到锚点处归零重来。
原因：**锚点制的 delta 是"相对锚点的累积差异"**，不是"相对上一步的差异"。
- 这是**有意**的（见 `src/snapshot.js` 的"不变量"注释）：相对上一步的 delta 会让"锚 + delta"**恢复不出当时的世界**——
  我第一版就是这么写的，实测**只有 delta 份全错、full 份全对**（症状：`events` 里出现 `null` 洞、被删的权重键又回来）。
- 代价：15 份窗口里，最旧那几份 delta 最大（≈24 KB），窗口总量 ≈ 3 份 full + 12 份 delta。
- **要不要改**（可选，属改已报批数字/机制）：
  (a) 维持现状（正确性优先，窗口 ≈ 数百 KB）；
  (b) **锚点加密**（`ANCHOR_EVERY` 5 → 3）：delta 变小但 full 变多，总量未必更省；
  (c) 改回"相对上一步的 delta + 基线重写"：delta 最省，但修剪要折叠基线（本实施刻意躲开的那类 bug）。
- **我的建议：(a) 维持**——正确性已锁死、量级可接受；等你看到真账长跑数再定。

### 7.3 ★待决 B：面板第八页签的实机未验（Ctrl+F5 后看）

`设置 → 快照`：应显示「快照 N 份 · 覆盖第 a–b 轮 · xxxKB」，每份一行带「回到此步」。
若为空：①世界还没落过账（推一轮就有）②IndexedDB 被浏览器策略挡了（看控制台 `[story-world-v2] 快照失败`）。

### 7.4 实施期的四个真 bug（**都是实测抓到的，不是推的；全部留档防复发**）

| # | 病 | 抓到它的判据 |
|---|---|---|
| 1 | `applyDelta` 数组删除用 `splice` 挪位 ⇒ `set['arr/i+1']` 写到错位置、整段搬家（症状：`events` 出现 `null` 洞） | 往返逐字节锁 |
| 2 | 深拷时"合并另一方向"写成了"合并**自己**那张表" ⇒ 刚删的键被 `del` 自己写回（`e_bk_2` 删了还在、跑到末尾） | 往返逐字节锁 |
| 3 | `deepCopy(base)` **漏传两个 delta 表** ⇒ 退化成浅拷 ⇒ **就地改写调用方的世界** | "不改写入参"锁 |
| 4 | 序号解析 `Number(id.replace(/^s/,'')) \|\| 0` **静默降级成 0** ⇒ 保留窗口排序全乱（"留最新 15 份"实际留了任意 15 份），而**"窗口内每份可恢复"这条锁发现不了它**（乱序窗口照样自洽）——只有 `keepId` 那条抓到了 | `keepId` 锁 |
| 5 | 锚点间隔按 **tick 差**算 ⇒ 一步走多轮时**第 2 步就又落锚**（实测锚点变成 s1/s3/s5…，白占一倍空间） | 锚点分布断言 |
| 6 | 锚点 delta 算成"相对上一步" ⇒ 恢复时中间步全丢（同 §7.2） | "窗口内每一份都能恢复" |
