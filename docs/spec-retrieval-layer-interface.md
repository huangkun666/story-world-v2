## 4. 接口（本笔只定形状）

### 4.1 消费方（用户点名要求"不只给聊天 llm 用"）

| # | 消费方 | 它要什么 | 状态 |
|---|---|---|---|
| 1 | **世界模型**（世界步的包） | 往事（来路/经过） | ★**B2 就是它** |
| 2 | **聊天模型**（写正文的笔） | 账本历史（"那件事后来怎么样了"） | 现在**拿不到**（账在 `chat_metadata`，注入走 `web/inject.js`，**不是包**） |
| 3 | **面板**（给人看的窗口） | 同上，可翻可查 | 现在只有手翻编年页 |

### 4.2 契约形状（照 `recall.js` 那套，不新造）

现有的检索是一条"**取数 → 写账 → 出包时读**"的三段流水：

```
① 取数：recallWorldBook({ ssot, picks, store, limit, maxChars })
     → { chunks, reason }            ← 逐块 { text, source }
② 写账：noteRecall(ssot, res)        ← 记"这一轮检索了什么·命中几条"（自证面）
③ 读：  ssot.meta.recalledText  →  包里的 pack.recalled
```

**检索层要统一的，就是 ① 这个形状**：`fetch({ ssot, picks, limit, maxChars, sources }) → { chunks, reason }`。
★**关键纪律（三条，全部照抄 `recall.js`）**：

1. **只读、零副作用**：检索器**不写账**（只返回结果；写账那一步由编排层做）；
2. **失败零阻塞**：检索器没装/没开/抛错 ⇒ **一律返回空**，世界照常推进（`recall.js:81`）；
3. **如实上报**：`reason` 必须能区分"没命中"与"根本没在检索"——★这条是有血证的：
   `START-HERE.md:1298` 记着「**返空是静默的**……界面分不出"没命中"和"根本没在检索"」。

### 4.3 ★后端不要绑死（同 D3 那个病）

`recall.js` 现在只有一条腿：`yuzuki-Memory` 的单例，那个插件没装 ⇒ 整条路不可用（`recall.js:64` 直接返回"检索器不可用"）。

**账本检索要**多消费方共用**，就不能也只有一条腿**。建议后端降级链：

| 顺位 | 后端 | 好处 | 代价 |
|---|---|---|---|
| 1 | **向量库**（`yuzuki-Memory`，现成） | 能搜"意思相近" | 绑死那个插件（与 D3 冲突） |
| 2 | ★**结构化直取**（账本自己就有指针） | **零依赖**：账本的事实本来就是结构化的——实体 id、事件 id、轮次、`source.ref` 全是现成的 | 搜不出"意思相近" |
| 3 | 关键词 | 兜底 | 最弱 |

★**本细案优先第 2 位**：`leg109b` §4 第 1 问里"我的倾向"就是「**②起步**——账本的事实本来就是结构化的」。

### 4.4 检索源清单（B3/E1 的落点，**分层接入**）

| 层 | 源 | 备注 |
|---|---|---|
| ① | **编年**（含"来路/经过/收场得失"三类话） | ★B2 用的就是它；**唯一存本**（见配套细案 §2.2） |
| ② | **事件表**（含 `source.ref` 因果边、`closed` 记号） | 结构化；注意 20 轮以上会被归档压成里程碑 |
| ③ | **卷库**（`storage.js` 的旧卷） | 只存不检索（E1）；跨卷检索要先解决"卷是有序段"这件事 |
| ④ | 实体账 / 事件表 / 盘算表 | 结构化直取的主场 |
| ⑤ | ★**跨聊天** | **不是技术问题，是隐私边界**——见 §6 |

## 5. ★★"晚一轮"其实是**三种东西**，风险差一个量级（这一节最要紧）

用户说「**之后落地检索层的时候把这些晚一轮的设计都给重构了**」。这里头有**三种**，**不能一锅端**：

| 类 | 有哪些 | 性质 | 能不能"重构"出来 | 风险 |
|---|---|---|---|---|
| **① 接口统一** | `lookupScales` / `刻度补` | 路径本来就是通的（当轮取、下一轮递）⇒ 只是让它**也走检索层这根线**，好与账本检索共用 | ✅ 能（**等于改接口，不改语义**） | **低** |
| **② 通道改造** | 账本检索本体（现在没有） | 新代码，**从第一天就按"出包前检索、当轮交付"做** | ✅ 能 | **中** |
| **③ 语义决策** | `entityUpdates`（改属性）"模型看不到自己刚写的值" | ★**这不是重构，是产品决定** | ❌ **不能** | **高** |

### 5.1 ★为什么第 ③ 类必须你拍（不能由 agent 顺手改）

模型写了一句话改某人的属性（比如"实力 T9"）。**这一轮里，它自己该不该看见这个值？**

| 选项 | 后果 |
|---|---|
| **该看见** | 它看到的是**自己还没被引擎裁定的提案**（可能下一轮被引擎拒掉/改掉）⇒ 模型可能拿一个**还不存在的事实**往下写 |
| **不该看见**（现状） | 它要等落账后的下一轮 |

这撞的是承重墙：`STATE.md` §0 ——「**写账只有引擎能做**」。
⇒ **这一条是"账房与笔的分工"问题，不是代码形状问题。**

★**顺带一条既有先例**：`leg34` **已经替"查回来的字段"做过一次这个决定**——
`pack.js:905` 那格"已取回字段"（`meta.entityFields`），注释写明目的是**让模型当轮就能看到它刚查回来的值**，否则「模型问完还是不知道答案，**这条通道等于白问**」。
⇒ **同一个问题，本仓已经答过一次**（答的是"该看见"），只是**没推广**到你这一类。**要不要推广，是你的决定。**

### 5.2 顺序（按风险从低到高，**不搞大爆炸式重构**）

1. **B2 先落地**（并做成检索层的第一个消费方）；
2. **同批**给 `recall.js` 加**可插拔的检索源**（它已经有 `store` 注入面 ⇒ 加一档"账本源"，**旧路径逐字节不动**）；
3. **账本检索层立项**（分层接入：§4.4 的 ① → ② → ③，每层各出曲线）；
4. **最后**才碰第 ① 类（`lookupScales` 统一）；
5. ★**第 ③ 类（属性写回可见性）单独立项**，不混在这一串里。

### 5.3 ★一致性风险（不做第 4 步的后果）

第 2、3 步落地后，**必须**接着做第 4 步。否则"晚一轮"从**一处变成两处**——
**一半当轮、一半晚一轮，比现在更难查**。⇒ **这一串是个整体，不许只做前两步就收工。**

### 5.4 ★另一条不许越的界：同轮交付**只给料，不给裁定**

把"当轮"用过头会变成「模型在一轮里拿**两次**新数据」（先检索结果、再自己的提案）⇒
**世界步就不再是"一次提案、一次裁定"**。
⇒ 口径：检索层只负责**给料**；**裁定仍归引擎，账本只由引擎写**（§0 承重墙）。
