## 0. 一句话

**编年的往事有两条"变短"的路：一条会记账，一条不记账——而第二条会把第一条的诚实盖掉。**

| 路 | 谁干的 | 会不会说出来 |
|---|---|---|
| ① 包预算不够 → 裁往事 | `trimPack`（`pack.js:1166/1192-1218`） | ★**会**：包里写 `trimmed`（`纪事` = 整栏没装下 · `纪事.留N条` = 只装下最近 N 条） |
| ② 编年太长 → **轮转进卷** | `rotateChronicle`（`storage.js:74`） | ★**不会**：编年**直接少一半**，而 `trimPack` 那一刻量到的是"缩水后的编年"，它**全装得下** ⇒ `trimmed` 依然是 `undefined` |

⇒ **轮转那天，包里写着"什么都没裁"，而模型知道的往事少了一半。**
本细案要把第②条路接到**检索层**上，让卷里的往事重新可见——**顺便让它不再是静默的**。

**三个名词，当场说人话**：

- **轮转 / 入卷**：热账（存在聊天文件里的那本账）里的编年太长时，把**最旧的一段**剪下来、整段搬进浏览器本地一个叫"卷"的地方存着，好让热账不变胖。剪下来的那一段就叫一卷。
- **检索层**：专门负责"从账上把往事取回来"的那一层代码，就是 `src/ledger-recall.js`。
- **纪事**：每一轮递给**世界模型**的那份输入（下面叫"包"）里，装"世界已经发生过什么"的那一栏。`leg118` 刚把它的取数接到检索层上。

## 2. 治法：**只接一根线，不新造机制**

### 2.1 接口：照 `recall.js` 那条现成的路，不新造

`recall.js:59` 的 `recallWorldBook({ ssot, picks, store, limit, maxChars })` 早就是这么干的：
**`store` 由调用方注入**，缺省才去取浏览器里的单例；Node 里取不到就返回 `null` ⇒ 判据塞一个假的进去就能真跑。

⇒ 账本检索层照抄同一条：**给 `recallLedger` 的查询里加一格 `volumes`（已经取出来的卷），缺省不传 = 与今天逐字节相同。**

### 2.2 ★为什么不让检索层自己去取卷（两条硬理由）

| # | 理由 |
|---|---|
| ① | **`recallLedger` 是同步纯函数**，文件头写明这是刻意换来的性质：「Node 里可直接真跑，判据不需要造环境」。取卷要走 IndexedDB ⇒ **异步** ⇒ 这个性质当场没了，而且**改不回来**——`buildEvolutionPack`（`pack.js`）是同步的，它的调用链上没法等一个 Promise。 |
| ② | 本仓已有分工：**取数是检索层的事，I/O 是编排层的事**（`spec-retrieval-layer-interface.md` §4.2 第 1 条"只读、零副作用"）。卷的 I/O 归编排层，检索层只管"拿到手的这些行怎么取"。 |

### 2.3 顺序口径（**卷在前、热账在后**）

卷里放的是**最旧**的那一段，热账是新的 ⇒ 合并时 **`[...卷行, ...热账行]`**，整体仍是"从最早到现在"。
这样 `modeRecent` 那句"倒着给"（`chron.slice().reverse()`）自然还是**最新在前**，与 `leg116` 统一的排序口径不打架。
★**不重排**：卷行本身在卷里就是按轮次升序的（`rotateChronicle` 的 `sorted.slice(0, volLen)`）；即便不是，`newnessOf` 那一步也会把"平铺型"的取法排对。

### 2.4 I/O 与缓存放在编排层——**现成的两行就能复用**

`web/index.js:2722-2724`（**导出**那条路）已经在做这件事：

```
const volumes = await volumeStore().list();
const full    = await Promise.all(volumes.map((v) => volumeStore().get(v.id)));
```

⇒ 接线时照抄这两行，把 `full` 缓存起来即可。**摊销成本≈0**：卷只在轮转时追加、极少变；而失效点**已经存在**——`LISTED_VOLUMES` 每次载入都会重新赋值（`index.js:1942/2070/2926…`），缓存跟着它一起刷就行。

### 2.5 一处设计取舍（我建议这版，理由在下面）

| 方案 | 做法 | 评价 |
|---|---|---|
| **甲（建议）** | 查询里显式加 `volumes`，层内建一条 `chronicleOf(ssot, q)` 给七种取法共用；`timeMarkAt`/`groupByTime` 同样收这一格 | ✅ `ssot` **仍然只表示"热账"**，不会被误读成"全账"；照 `leg117` 给 `archivedById` 的做法（同样是"把够不着的东西递进查询里"） |
| 乙 | 加一个 `withVolumes(ssot, volumes)`，返回一份 `chronicle` 已合并的 `ssot` 副本 | 改动面更小（七种取法与 `timeMarkAt` 一个字不用改），但 **`ssot.chronicle` 就不再等于"热账"** ⇒ 下一个读代码的人会以为 `events`/`agendas` 也被合并了（它们没有，轮转只动编年） |

⇒ **建议甲**：本仓刚为"两把尺子/两个意思同一个名字"付过账（`leg118` §4.1 栏级那把尺 vs 包级那把尺），不宜再引入一个会歧义的名字。

## 4. "**也不压缩**"那一半：★可能是**非缺陷**（要你拍）

E1 的原话是"卷库只存不检索、**也不压缩**"。先把算术摆出来：

| 问题 | 数 |
|---|---|
| 卷存在哪 | 浏览器的 IndexedDB（`web/idb-backend.js`，表 `volumes`）——**不进包、不在聊天文件里**（只有"导出"才带上） |
| 它的体积影响什么 | 只影响浏览器本地占用 |
| 实测每轮长多少 | 654 字节 ⇒ 1 万轮 ≈ **6.5 MB** · 10 万轮 ≈ **65 MB** |

⇒ **容量上不需要压缩**（今天不需要，可预见的一万轮内也不需要）。
⇒ 而"压缩"若指**写一段摘要**：那是要**新写一段账上没有的话**——**撞承重墙**（`STATE.md` §0：「引擎**不发明事实**」）。
⇒ 机械压缩（丢掉机械记账行）**已经有了**，而且在**消费者面**做（`isChronicleBriefLine`，`chronicle-brief.js`）——卷里留着全量反而是对的：**卷是唯一存本，消费者各有各的取舍。**

★**所以"不压缩"这半条，要么是非缺陷（容量上不需要），要么是一个产品决定**（要不要让模型给旧卷写梗概）。
**本细案不替你定**，也不把它和"接线"混在一起做（照 `spec-retrieval-layer-interface.md` §5.2 那条"不搞大爆炸式重构"）。
