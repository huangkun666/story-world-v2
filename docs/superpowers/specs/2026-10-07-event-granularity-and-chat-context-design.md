## 3. 现状为什么会这样

1. `web/inject.js:248` 的规范要求把动过手的人逐行标出来。`src/settle.js:1145` 的 `registerDialogueFacts` 把每条行动、变化、承诺分别建成事件；变化又单独落格。所有这些事件出生时都是 `closed:false`。
2. 世界侧 `newEvents` 则有来源、因果与波及名单，`entityUpdates` 负责状态改变。两条路对“什么是一件事件”的定义不同，换一句提示词无法消除落账结构的差别。
3. 聊天事实在世界模型输入里有多个落点：`turnFacts`、`pendingEvents`、`纪事`，以及可能命中的往事。`src/tick.js:288` 先注册，再出包；`src/pack.js:1202`、`:1402`、`:1493` 分别提供这些入口。同一事实可能既作为当前事实又作为未决事项和历史重复出现，需要对完整输入逐项统计。
4. `src/ledger-recall.js:161` 合并热编年和冷卷，聊天注入直接使用这些行；`web/inject.js:822` 的关键词候选和 `:833` 的向量候选均没有聊天来源过滤。候选到了纯文本格式化阶段就更难分辨是谁产生的。
5. `ledgerDivergenceText` 还会提供聊天改定的当前状态。这里应与事件回流区别处理：“黄坤现在是外籍特权学生”是需要保持一致的状态；把“递交证明”再讲一遍则是重复事件。不能一刀删除所有聊天产生的状态，否则模型会退回书里的旧身份。
6. 当前消息消费主要依赖内存中的正文比较，事件没有稳定地指回具体消息版本。重试、刷新、手动推进和重生成的语义需要分清；不能按标题相等断言同一笔事实已经处理过，也不能把不同消息里的重复行为一律删掉。

## 4. 三种方案与推荐顺序

| 方案 | 做法 | 取舍 |
|---|---|---|
| 先止回流 | 统一辨别事件来源；聊天侧的关键词、向量、冷卷和维护记录走同一规则；保留必要的当前状态。 | 范围较小，先消除已经证实的重复；仍不能解决“每个动作都是事件”和世界模型输入里的噪声。适合作为第一步。 |
| **推荐：统一事件定义，再统一输入组织** | 普通动作不自动建未决事件；聊天只提交有后续影响的结果与承诺；世界模型拿到一次简洁事实和必要状态，不再看到同一事实的多份正文。 | 同时处理用户的两个主要问题；需要同步调整标签、落账、当轮行动保护、因果引用和输入组织，并在副本上验证。 |
| 另加一次模型汇总 | 让另一个模型调用把全部动作重新合成大事件。 | 会增加延迟、费用和一个新的失败点；若原始动作仍全量进主调用，注意力问题仍在。暂不采用。 |

建议分两步交付：第一步单独修回流，第二步落地统一事件定义与世界输入。宿主和保存的验证贯穿两步。不要在一笔里顺手重写整个引擎。

## 5. 共同的事件定义

一件事件应是一项已经发生、能改变后续局面的事实结果。它可以改变身份、资源、控制权、关系、计划条件或参与者对局面的认识；也可以确立尚需兑现的承诺。不是按规模或标题长度判断：一句约定也可能比一场盛大会议更有后果。

模型负责决定哪些事实满足这个定义，引擎只检查身份、结构、重复消费和引用是否合法，不用动词表、分数或文本相似度替模型判断重要性。

| 真账例子 | 推荐记录方式 |
|---|---|
| 多人问候、返回班级、分发普通资料 | 原聊天仍完整保留。若没有改变后续条件，不自动建独立事件，也不送入世界主调用当待办。 |
| 递交特权证明，获得外籍特权学生身份 | 一个事实结果，例如“黄坤取得外籍特权学生身份与对应许可”；状态更新关联这件事，不再另建一件“递交”加一件“身份变更”。 |
| 改革宣言 | 如果只有礼仪发言，无新约束则不登记事件；如果确立具体规则，记录“谁宣布了什么规则，实际改变了谁的条件”。由写出正文的模型判断，插件不猜。 |
| 接受封锁消息、每月进贡的承诺 | 记录一个约定，明确参与者与义务；后续违约或履行由世界演化产生新结果，不逐句重复登记“承诺又说了一遍”。 |
| 一场戏出现两项互相独立的变化 | 分成两件事件，不强迫“一场戏只能一件”；不能为压缩而把不相干的事实粘在一起。 |

聊天协议保留现有 tags 围栏与身份解析，增加明确的事件摘要及关联结构；旧标签通过兼容入口读取，不要求玩家重建世界。实施前确定版本化的具体字段。必要字段是：本消息内事件编号、结果摘要、参与者、已知时间/地点、关联的变化或承诺、已有因果引用（有才填）。消息身份由宿主适配层补齐，不要求聊天模型编 ID。不得恢复原文引用一致性拒收规则。

普通动作标签可用于本轮“这些人已经行动过”与玩家实际落子的保护，但不再自动成为独立故事事件。原文和原标签留在原消息，插件保存消息版本指纹与处理结果的指针；避免另存一份完整动作流水账长期进入世界输入。

## 6. 世界模型输入：防止聊天材料夺走焦点

世界模型需要读聊天确立的新事实，并在此基础上演化世界。减少的是无效详情和重复，不是把有用的聊天事实从世界里屏蔽。

输入组织遵守以下规则：

1. **当轮聊天事件只提供一份正文。** 出现在“本轮已经发生的结果”后，其他栏目对同一事件只保留必要 ID 或不再重复。这个判定在最终包组装时执行，不能只在某个检索口去重。
2. **当轮行动保护与事件正文分开。** 传紧凑的“本轮已行动者 ID”和“本轮已改定的实体/字段”，继续防止世界模型重演聊天动作、重改同一格。这个机制不能依赖“聊天所有动作都必须是事件”。
3. **已完成动作不默认占未决列表。** 只有仍有明确未完成义务、争端或追踪目标的事项才列为未决。事件已经发生、后果仍可能继续，并不等于它必须一直开着；关闭记录仍可作为后续因果源，归档也必须保留来路。
4. **先取消重复，再应用现有总预算。** 不额外添加聊天硬配额，不靠固定条数掩盖噪声。若单轮确有多项独立重要变化，要完整保留；世界输入应继续有自身正在推进的事情，不能因为聊天材料占位而悄悄裁掉它们。
5. **历史按相关性取一次。** 当轮已提供的事实不再由纪事或向量回收一遍。世界模型可检索过去重要的聊天事件，但纯维护记录和低价值动作不成为历史召回正文。
6. **提示词写清阅读任务。** 本轮聊天结果是既成条件，世界模型要提出新的影响和变化，不复述、重演或替玩家决定下一步。

验收时记录整包中“聊天新结果”“世界待办/动态”“相关历史”“结构保护”的字符或 token 估算，以及每个事实正文的出现次数。统计只说明输入组成，不能宣称直接测到了注意力。对照运行观察：重复演已完成动作、遗漏世界待办、只围绕聊天人物产事等具体行为是否改善。

## 7. 聊天上下文：只带世界产生的新结果

建立一个共用的来源判断，在纯文本格式化和预算选择之前调用。候选信息至少区分“谁产生的”与“这是什么记录”：聊天/世界/设定/未知；事件结果/当前状态/生命周期维护。因果来源与生产来源分别保留，不能混为一格。

- **聊天自己提交的事件摘要不回到聊天。** 关键词、向量、冷卷和最终写入提示词都遵守同一规则；向量候选被过滤后要从剩余合格候选补位，不能先占 top-N 再全部丢掉。
- **世界产生的新后果正常注入。** 世界因聊天承诺而产生制裁，虽然因果指向聊天事件，生产者仍是世界模型，必须带给聊天。不能沿因果链把所有后续事件一并剔除。
- **当前状态仍提供一次。** 身份、位置、关系等确已改变的状态维持一致；状态段与其他注入段按实体/字段合并，避免再叙述一次改变经过。来源于聊天不是删除最新状态的理由。
- **纯维护记录不讲给聊天听。** “问候已收场”“盘算推进一步”“模型把事件关闭”等只保留在账和报告；若收场包含一个新事实结果，那个结果单独作为世界事件提供。
- **世界动向保留现有干净的生产链。** 补一致性核验，不能为了这次修复把整份编年改为动向输入。

来源信息要随事件、编年、冷卷和索引取回结果保持一致；新增字段必须登记到现有 schema，不能以“不改契约”名义写入未知字段。索引仍可供世界侧检索聊天事件，不应为了聊天过滤而全局删除这些向量。

旧记录优先用 `eventRef`、`chainRef` 关联热事件及里程碑里保留的事件来源恢复信息。已知登记函数产生的行 ID 可作为确定的兼容证据；不能只靠事件位次、标题相似或“没有 eventRef”猜来源。确实辨不出的标为未知，保留旧行为并在复制报告统计；不删除旧账来伪造过滤完成。

## 8. 消息消费与保存：防止同一轮变成两轮

每次聊天结果处理需带聊天身份、消息身份、选中版本/重生成版本和内容指纹。宿主没有稳定消息 ID 时，在可保存的消息扩展字段登记插件 ID，而不是用会随删除变化的数组位置充当唯一身份。登记方法分别用官方 ST 和 TT 的实际消息形状验证。

处理结果与世界账同一笔保存：消息版本已经消费、产生哪些事件、哪些字段发生变化、对应世界版本。保存失败不先登记“已消费”；重试也不重复写事件。主调用结束后的提交再检查当前聊天与世界版本，切聊天或回档后的迟到结果作废。

手动推进世界但没有新的助手消息时，只推进世界，不再次注册末条聊天标签。刷新后已消费身份仍可读到，不依赖内存中的最后一段文字。

编辑、删消息和切换重生成版本不能悄悄撤掉已经导致多轮世界变化的事实：

- 尚未提交的结果可以替换待处理版本。
- 已提交的最新一轮若要更换，先从该轮前的快照生成副本重算并核对；较早消息的变更需回到受影响轮前，再按后续确定输入重放。原账保留，在提供可核对的重算结果后再进行世界替换。
- 同一段文字出现在两条不同消息里，不等于同一事实；同一消息重复回调也不等于又发生了一次。仅靠正文或标题去重都不能解决这个问题。

## 9. 社区故障的具体打磨

| 故障层 | 先看什么 | 有用的验证 |
|---|---|---|
| 宿主保存 | 宿主类型、实际调用保存接口、成功回读的世界指纹、完整错误文本 | 官方 ST/TT 各验证开局、推进、刷新回读；保存失败和覆盖冲突分别验证，不拿官方 HTTP 路径的时延规则套 TT。 |
| 卡与世界书形状 | 顶层/data 文本长度、懒加载标志、书来源、在不在角色聊天 | 顶层空串但 data 有正文、真空卡、懒加载、无世界书；同一个取法同时管“判空”和“读取”。 |
| 标签与事件 | 围栏是否找到、实际解析条数、身份未解析数、实际新增事件、状态未变数、消息版本 | 真实模型格式副本、块外引用、转义/截断标签、旧协议；报告能解释少记在哪一步，不只打 console。 |
| 重试/切聊天/回档 | 当前作用域、队列/异步任务、世界版本、提交结果 | 请求未结束时切聊天或回档；保存失败重试；手动推进；刷新后重复回调。 |
| 手机操作 | 完整操作入口、当前设备与浏览器、具体可复现步骤 | 触屏打开下拉框/弹层、切页、运行中重绘；实际宿主里跑，不能只用桌面截图代替。 |

每个社区复现形成最小可回放的输入和真实行为断言。继续保留全量测试，但把宿主行为、输入形状、消息生命周期和最终模型输入作为发布验证的重点。复制报告增加事件来源计数、最终选入的事件 ID、跳过原因、世界包重复次数和保存结果；具体正文默认不扩展显示。

## 10. 交付与验收

**第一步：停止事件回流。** 统一来源与记录类型，处理关键词/向量/冷卷，保留当前状态，覆盖历史兼容；在已复制的两份账重放最终注入，确认聊天事件标题不再由事件段回流，世界产生的新后果仍在。对未知来源单列实际数量，不能报成零泄漏。

**第二步：统一颗粒度和世界输入。** 同一校园输入里，纯问候/普通资料不生成独立未决事项；身份和许可合成一个明确结果；承诺与独立冲突按各自影响保留。同一事实在完整世界输入里正文只出现一次，当轮行动和字段保护仍生效，世界待办仍完整。

**两步都须通过：** 官方 ST/TT 的保存回读；重试不重复消费；世界仅推进时不重读末条聊天；切聊天/回档拒绝迟到结果；归档/冷卷后来源仍可辨；重要状态不退回书中旧值。做完再用真模型对固定副本和固定输入跑对照，记录实际行为改善与剩余误差，不能拿测试数量代替模型质量。
