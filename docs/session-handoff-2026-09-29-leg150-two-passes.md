## 2. 交付（一笔，两件）

### 2.1 甲案：起根并进第二遍（`3N → 2N`）

**改之前**：初始化把**整本书读三遍**——名册一遍（`chunk`）· 属性＋设定一遍（`attrs`）· 起根一遍
（`seedRoots`）⇒ 三国 14 块 × 3 = **42 次调用**，三路并发 ≈ **21 分钟**。

**改之后**：起根**并进第二遍**——第 2..N 块在那一次调用里**顺带**问一句"书里正在发生的事"
⇒ **28 次调用**（−33%）。

**为什么成立**（细案 §2.1 三条，都核过）：
1. **两遍的块是同一刀切的**（`chunkRows` 与 `chunkBookText` 同一个算法、同为 30000）；
2. **候选名单在这一刻算得出来**——名字第一遍跑完就有（`rawBookNames`），而"**被事件点名过的**"
   在开局那一刻**恒为空集**（**起根本身才是这个世界的第一批事件**）⇒ 那条过滤一个人都不筛掉；
3. **次序不冲突**——起根排在后面的唯一理由是"玩家别混进候选池"，而合并之后
   "**问**"在第二遍、"**落账**"仍在最后（与现在同一处、同一时机）。

**落地的层次**（照细案 §2.2 那张表，逐层）：

| 层 | 落了什么 |
|---|---|
| **契约层** | 第二遍的输出形状多一格可选 `roots`；它的**形状对象与单发起根共用一份**（`SEED_ROOT_ITEM_SHAPE`），那一问的**正文也共用一份**（`seedRootsBrief`）——★各写一份必然漂移，而漂移之后**没有任何判据会红** |
| **引擎层** | `buildAttrsOnlyPrompt(t, declared, { roots })`——**不给 `roots` 就与旧版逐字节相同**；`sanitizeCanon` 把 `rawRoots` **原样带出**（与 `rawRelations` 同一个治法：块级只负责"别丢"）；`extractWorldSetting` 在第二遍**逐块过出处闸**（原话必须真在**这一块**里）、**按块序**堆进 `rawRoots` |
| **编排层** | `web/index.js` 按 `Array.isArray(r.rawRoots)` 分叉：**有** ⇒ `seedRootsFromPass`（直接落账，**一次调用都不再发**）；**没有**（小书单发／命中书指纹缓存）⇒ 照旧 `seedRootsForWorld` |
| **收口** | 跨块去重（**按块序**）＋ 总量上限 ＋ 幂等指纹 ＋ 当事人必须在账上——**一处定义**（`seedRootsFromPass`／`dedupeRootsAcrossChunks`），`seedRootsChunked` 那条老路**改走同一个收口** |
| **保留** | `seedRootsChunked` **一个字没删**：它还被四条路用着（换书重种 · 存量移植 `demo/seed-roots-migrate.js` · 载入期自动补根 · **小书单发**） |

★**P2 口径**（用户拍的）：`roots` **只塞第 2..N 块**——首块不塞。判据钉着这一条。

## 4. ★★ 本笔最值钱的四条

### ① ★★★ **用户那句反问比我的选项表值钱**——"为什么会这样"才是他真正在问的

我接手后按纪律把活儿单摆成一张选项表问他"是哪一件"。**他没答**，反问了一句

那一条往往才是他要做的。

### ② ★★ **"每块都问"降成"只问一次"这种优化，前提一定要能被推翻**

丙案的病根不在"某处写错了"，而在**leg61 当年一个没被验证的前提**（"设定只在头一块"）。
它看起来完全合理（书里设定类条目常排在前面），于是**写进了提示词、还配了注释解释为什么**——
而 leg63 早在另一个通道上**实测推翻过它**（大荒首块只覆盖 **10.1%**），
**那个修却只落在「只重抽设定」那条路上，初始化这条路没收口**。
⇒ ★**同一个前提活在两条路上，只修了一条** ——这是本仓"规矩只长在一条路上"那张老卡的第 N 次现形。

### ③ ★★ **一处定义的地方要多问一句"另一条路会不会自己写一份"**

这一笔新增的每一个纯函数（`rankSeedCandidates`／`maxRootsPerChunk`／`seedFingerprint`／
`dedupeRootsAcrossChunks`）**都不是为了好看**，而是因为甲案让起根有了**两条路**：
一旦各写一份，**幂等指纹会算成两个串**（同一本书被种两遍根）、**每块上限会不一样**、
**候选排序会分叉**——而这三件事**红了也不会有人知道**（世界照跑，只是根少了/重了）。
⇒ ★判据里专门有一条钉着："**两个入口产出逐字相同的名单**"、"**指纹串形与老口径逐字相同**"。

### ④ ★ **写棘轮时我自己假红了两次，两次都是同一个病：判据咬词面，不咬语义**

1. 丙案那条我写 `assert.ok(!p.includes('力量谱系'))` —— 而**"力量谱系"恰恰出现在这一份的反面说明里**
   （「设定（力量谱系/法则/…）**本遍不要**」）⇒ 一写就红，红的是我的判据。
   改成**咬形状**（`Object.keys(parsed)` 只剩 `entities`）才对。
2. 候选名单那条我写 `assert.ok(名单.includes('条目0'))` —— 而排序键是"**这名字在书里出现多少次**"，
   `条目1` 会因为**子串**出现在 `条目10/100…` 里而排到前面 ⇒ **排第一的不是书里第一个名号**。
   那不是病，是"排序键在干活"。
⇒ ★**教训与 leg149 §4③ 是同一条**：写完棘轮问一句「**这条红，红的是它还是我？**」
