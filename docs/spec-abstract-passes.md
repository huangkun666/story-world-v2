## 0. 人话版：这会怎么样

现在你开一个新世界，模型要把你**整本世界书从头读三遍**：名册一遍 · 属性＋设定一遍 · 起根一遍。
一本三国那么大的书 ≈ **42 次调用**，三路并发下**约 21 分钟**（这正是你昨天跑出来的那个数）。

本细案主要做一件事：**把「起根」那一遍并进「属性＋设定」那一遍。**
两遍读的本来就是**同一刀切的同一批块**，所以完全可以一次问完。
⇒ **42 次 → 28 次，约 21 分 → 约 14 分**（−33%）。

而**起根要的那份「优先挑这些人」的候选名单不会丢**——它是**纯函数**，第二遍跑的时候料已经齐了
（名字从第一遍来、书文本来就在手、人设名随时读得到）。

★另外查到一件**只值钱在"抽得全不全"上、不省时间**的事：名册那一遍现在一口气问**七样**东西，
而**本仓自己量过**——七样一起问，**名册产量掉到三分之一**（1022 → 364 个名号）。
这一件**要不要动得先复量**（当年的装置没了），所以它在本细案里只到"拍板点"为止。

## 2. 甲案（省时间）：起根并进第二遍

### 2.1 可行性三条（都核过，不是推理）

1. **块是同一刀切的** ⇒ 第二遍跑的时候，起根要读的块**已经在手上**，不用重切、不用重读。
2. **候选名单在第二遍时算得出来**。`buildSeedCandidatePool`（`web/index.js:1830`）只要三样：

   ```js
   const named = new Set();                                  // ① 被事件点名过的
   for (const e of hotWorld?.events || []) for (const r of e.ripples || []) named.add(r);
   return (hotWorld?.entities || [])
       .filter((e) => active && !named.has(e.id) && e.id !== playerId)
       .filter((e) => name.length >= 2 && name.length <= 12)
       .filter((e) => !/[<>{}]/.test(e.name))
       .sort((a, b) => b.n - a.n || ...)                     // n = 这名字在书里出现多少次
   ```

   - **①「被事件点名过的」在开局那一刻恒为空集**——**起根本身才是这个世界的第一批事件**
     ⇒ 这条过滤在初始化时**一个人都不筛掉**。
   - **名字**：第一遍跑完就全有了（`rawBookNames` → `dedupeRoster`）。
   - **书文原文**：本来就在手。
   - **玩家自己**：`personaName` 读自 `getCtx().name1`，随时可读（`web/index.js:2858`）。
   ⇒ **料齐了。** 唯一要动的是把"从实体对象取名字"换成"直接从名册名单取"（一个几行的纯函数）。

3. **次序上不冲突**。现在起根排在很后面，理由只有一条（`web/index.js:2867` 逐字）：
   > 「★位置：**必须在 `attachPlayerPiece` 之后**——候选人名单取自"账上没被点过名的人"，
   >   棋子若还没建，玩家自己会混进候选池里」

   合并之后这条**照样满足**：根是在第二遍里**被问出来**的，但**落账仍然放到最后做**
   （与现在同一处、同一时机）。"问"与"落账"分开，这条约束就不受影响。

### 2.2 怎么改（分清层次）

| 层 | 改什么 |
|---|---|
| **契约层** | 第二遍的 JSON 形状加一格 `roots`（沿用 `buildSeedRootsPrompt` 已有的那个形状：`title`/`position`/`parties`/`quote`/`why`）。★这一格要升 `MAIN_PROMPT_V`。 |
| **引擎层** | `sanitizeSeedRoots` **原样复用**（它要的 `sourceText` = 那一块的书文，现成）。起根候选按 `maxPerChunk` 收口的口径也不动。 |
| **引擎层** | `extractWorldSetting` 多返回一格 `rawRoots`（各块先堆着，**按块序重放**——与 `rawCanons`／`rawBookNames`／`rawRelationsAll` 同一个治法，绝不改成完成次序）。 |
| **编排层** | `web/index.js`：`extractWorldSetting` 之后把 `rawRoots` 收下；`seedRootsForWorld` **加一条"收下已有的根"的入口**（或直接在落账那一步用），不再发第三遍调用。 |
| **保留** | `seedRootsChunked` **一个字不删**——它还被四条路用着：①「只重抽设定」那条路**不许起根**（意图不同，`skipRoster` 要显式隔离）②换书重种（`shouldSeedRoots` 指纹变了）③存量移植（`demo/seed-roots-migrate.js`）④载入期自动补根。**合并只发生在"初始化"这一条路。** |

### 2.3 风险（如实说，不藏）

1. **摊薄**——✅**已量（§6）**：**测不出摊薄**（合计乙臂反而 +2.1%、方向不一致、
   同臂内离散比两臂之差大一个量级；且乙臂每遍都真出了根）。
   ★**没说完的**：n=3/臂 ⇒ **小的真效应（如 10%）排除不了**（见 P6）。
   背景是 leg61 的血证：往一个调用里塞更多问题，产量会掉——所以这条**当初必须真跑才算数**。
2. **失败耦合变紧**。现在起根「逐块失败只丢那一块」、且**失败零阻塞**（`web/index.js:2869`：起根不成照常开局）。
   合并之后，一块失败会**同时**丢掉那一块的属性与根。⇒ 要么接受，要么在收口处把两件事的失败**分开记**。
3. **首块那份本来就大**（`CANON_SHAPE` ＋ `entities` ＋ `tension` ＋ `env`）。可以只把 `roots` 塞给
   **第 2..N 块**（它们只问属性，形状最小、地方最多），首块保持原样——这一步要在细案拍板时定，见 §3。

## 4. 验收判据（可测）

1. **调用数**：同一本书、同一个并发度，初始化期间的**完成段数**从 `3N` 降到 `2N`
   （N = 块数）。判据落在 `timing.calls`／进度事件的 `finish` 计数上（`test/abstract-chunk.test.js` 已有同款断言面）。
2. **块号仍然可见**（leg149 刚立的棘轮不许回退）：两遍都带 `index`/`count`，实施清单分得清是哪一遍。
3. **产物逐字节不变**（在关掉 `roots` 的前提下）：同一夹具下，`canon` 与 `ssot` 与合并前**逐字节相同**
   ——这是"只搬了问题、没改行为"的证据（本仓对并发化就是这么验的，`abstract.js:2396` 那条口径）。
4. **候选名单等价**：新算的候选池与"落账后再算"的候选池**逐字相同**（同一个纯函数的两个入口）。
5. **红线 1 不破**：玩家自己**不在**候选池里（现有判据 `test/seed-roots.test.js` 同族，要补一条）。
6. **`skipRoster` 那条路零变化**：「只重抽设定」**一次都不许起根**（补一条判据钉死）。

## 6. 前置数据：「摊薄」量过了（2026-09-28 · 三轮真跑 · 共 46 次调用）

**要回答的问题**：往第二遍（属性＋设定）塞 `roots` 之后，**属性与设定的产量会不会掉**？

**装置**（仓外只读，`F:/deepseek/tmp/leg149/`，照"一次性装置不进仓"）：
`leg149-attrs-roots-ab.mjs`（A/B ＋ `ab-inspect.mjs` 配对统计）。
★它用本仓**真的**合订器 `composeInitSource`、**真的**提示词 `buildSettingPrompt`/`buildAttrsOnlyPrompt`、
**同一把尺子** `chunkRows` ＋ `SETTING_CHUNK_CHAR`；乙臂只在**书文之前**多插一段 `roots` 说明。
书 = 用户真跑的那本《三国》（合订 500,184 字符 · 827 条 · 题名 189 · 切 14 块）。
★两臂**交错发在同一个池里**（甲c1,乙c1,甲c2,乙c2…）——否则后跑的臂会独自承受网关变慢，差异分不清是谁的锅。

| 轮 | 规模 | 结果 |
|---|---|---|
| 一 | 并发 3 · 前 6 块 | ★**作废**：12 次里 **7 次 HTTP 429**，只剩 2 个配对块；且两块乙臂的 `roots` 都是 `[]`（**treatment 没花输出 ⇒ 没有摊薄可测**） |
| 二 | 并发 2 · 全 14 块 | 27/28 成。**根只出现在 3 块（c6/c8/c9），全在书中段叙事部分**——头两块是人名册与设定，一条根都没有。★这一轮给出了**噪声地板**：11 个"`roots=[]`、treatment 等于没做"的块上，属性单块波动 **−50% ~ +60%** |
| 三 | 并发 2 · **c6/c8/c9 每臂 3 遍** | **18/18 全成，零失败**（下表） |

**第三轮（决定性的那一跑）**：

| 块 | 甲臂属性（3 遍） | 乙臂属性（3 遍） | 差 | 乙臂根 |
|---|---|---|---|---|
| c6 | [11, 5, 10] 均 **8.7** | [7, 10, 7] 均 **8.0** | −7.7% | 1,1,1 |
| c8 | [77, 92, 43] 均 **70.7** | [47, 91, 141] 均 **93.0** | **+31.6%** | 4,4,3 |
| c9 | [24, 106, 110] 均 **80.0** | [21, 113, 51] 均 **61.7** | −22.9% | 7,7,4 |
| **合计** | **478** | **488** | **+2.1%** | **32 条** |

**结论：测不出摊薄。** 三条理由，一条比一条硬：

1. **方向不一致**——c8 **升** 31.6%，c6/c9 降；**合计乙臂反而多 2.1%**。
2. ★**同臂内的离散比两臂之差大一个量级**——c8 的甲臂自己就在 **43→92**（2.1 倍）之间跳，
   c9 的甲臂在 **24→110**（**4.6 倍**）之间跳。两臂之间那点差**完全淹没在里面**。
3. **treatment 真生效了**——乙臂**每遍都出根**（9 次调用共 **32 条**），出字总量还**多了**
   （68,424 vs 63,832）。它不是"没干活所以没影响"。

★上一轮汇总表上那个「−58.6%」现在看得很清楚：**c9 的甲臂单独一块就能从 24 跳到 110**，
拿 n=1 的两个数相减，减出来的是噪声。**"一个总指标变好 ≠ 每一轮都变好"**（leg136 的老教训）在产量上也成立。

**★这一格没说完的部分（如实登记）**：n=3/臂、同臂离散 2–4.6 倍 ⇒ **小的真效应排除不了**
（真掉 10% 这个样本量也看不出来）。要点名排除得**每臂 10 遍以上**。
从"合计 +2.1%、方向不一致、离散压倒差"看，**没有理由认为它会掉**；但"证明它一点影响都没有"这句话**我不敢说**。⇒ 见拍板点 **P6**。

**一条顺带量到的**（与摊薄无关，但有用）：**并发 3 在这条网关上顶不住**——第一轮 12 次里 7 次 429；
**并发 2 是 46 次里 1 次**（一次 524）。这与 `abstract.js:323` 那条逐字留档（用户上次丢 4 块）同源。

- ★**本轮量出的一条副产品**（与甲案无关，但可能更值钱）：**根在本书里只出现在 3/14 块**，
  且都在**中段叙事部分**——头两块（人名册与设定）**一条都没有**。这直接支持"起根那 14 次调用里，

- ★**本细案不改任何承重墙**（账/引擎/契约的语义都没动），改的是**问法**与**编排**。
