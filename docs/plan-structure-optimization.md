# 细案（草案）· story-world v2 项目结构优化：**让"引用完整性"有单一主人**

> 性质：**细案（草案）**，两段式的第一步。**未经用户拍板 = 不得进入实施**（dev-process §1）。
> 来路：用户 2026-09-18 令「**所以我才想要优化项目结构，交接给下一任做吧**」。
>   —— 上一句是用户问「就凭你现在的感觉你觉得这个项目的架构是对的吗」，
>   而 leg66 的回答是：**骨架对，但重活压在一条没有单一主人的缝上**（原文与证据见 §1）。
> ★★**这份文档的用途是"防下一任干歪"**，不是"给下一任灵感"。每一条候选都带
>   **实测底数 · 判据 · 本棒不做清单 · 拍板点**；**没有底数的那一条，不许开工**。
> ⚠ 含中文的文件禁止用 PowerShell 读写（用 `read`/`edit`/`write`）；含中文的探针产物由 node 自己写 UTF-8。

## 0. 人话版：这会怎么样

这台引擎现在跑得对，但它"对不对"这件事的规矩，**散在四个地方**：递给模型的材料里、契约的形状里、
提示词里、结算复核里。四处都能各自说了算，没有一个地方是唯一权威。
后果不是它现在坏，而是**每次换个模型、换本书、多个字段，就有一处接缝对不上，
然后只能在真机上撞见、再由人肉一点点补**——我这两天修的三条 bug，根子全在这里（§1.3 有账）。

所以这次优化的目标是：**把"谁能引用谁、在什么时候能引用"收成一个地方**，
再把两个已经长到 2000+ 行的文件按**语义边界**切开。做完之后：
- 换模型/改契约时，**漏改一处会当场红**，而不是等真机上被拒一轮才发现；
- 新来的人能在一屏内看清"一次结算按什么顺序做了什么"，而不是去 130 行顺序过程里自己悟；
- **不改任何一座承重墙**：红线、"无源之物不存在"、"引擎不裁判"、零依赖、无构建，一个字不动。

## 1. 为什么是这个目标（底数与证据）

### 1.1 三个候选的真底数（本棒实测，不是印象）

| 候选 | 底数（可复算） | 它值不值得动 |
|---|---|---|
| **甲 · 引用完整性无单一主人** | 同一个 id 的合法用法散在**四处**：`pack.js`（给不给这个号）、`world-step.schema.js`（形状允不允许）、`prompts.js`（怎么教模型用）、`settle.js`/`check-step.js`（事后认不认）。★**本棒两天内三条 bug 全部出自这里**（§1.3） | ★★★ **值**：这是唯一"正在持续产生 bug"的一类 |
| **乙 · 结算是一条 130 行就地改的顺序过程** | `settleTick` = `settle.js:875→1003`（**128 行**），一路 `applyX(world, …)` 就地改同一个对象；**步骤先后本身在承担语义** | ★★ **值**：不是它长，是**顺序上的不变量没人守**（§1.2） |
| **丙 · 两个超大单文件** | `web/index.js` **256 KB / 3689 行** · `src/render.js` **195 KB / 2145 行** · `web/style.css` 51 KB | ★ **要动，但它是症状**：厚度是 66 棒在每个接缝处打补丁补出来的。**先做甲，再看丙** |

★**反面读数（防止"越大越乱"的错觉）**：真正的引擎是 `src/` **38 个模块约 1.1 MB**；
发布物 6.8 MB 里的大头是 `docs/`（2.6 MB）与历史探针（`demo/` 610 KB）——
**`docs/` 用户已拍板留仓**，那不是"结构问题"，别去动它。

### 1.2 ★★"自称防御的检查，实际在承担语义"——这条病的形状

`settleTick` 的顺序（本棒实读）：

```
applyAgendaAdvances(963) → closeEvents(966) → applyEntityUpdates(970)
```

而 `applyEntityUpdates` 里那句复核，**注释自称是"防御"**（"check 已核，此处是不信上游"）。
**W2f 用例证明它不是防御——它是承重的**：契约层说"因必须还没了结"，
可真正生效的位置在第 970 行。于是：

- 入口 `checkWorldStep` 看到因是开的 ⇒ **放行**；
- 同一批里 `closeEvents` 先把它关掉（源盘算满步结算 ⇒ "源结清"型）；
- 复核读到**事后状态** ⇒ 把**刚刚放行的合法变更吞掉**（真账实测：`meta.entityFields['e_bk_297']` 零留痕）。

⇒ **判据：凡是"顺序承担语义"的地方，必须有一个地方把那个顺序写下来并锁住**（现在没有）。

### 1.3 三条 bug = 同一个根（这是"甲"值得做的直接证据）

| 现象（都发生在 leg66 两天内） | 表面原因 | 共同的根 |
|---|---|---|
| 字段写回被吞（`ev_5_3`） | 复核读事后状态 | **同一个"因"，在检查期与结算期有两套判据** |
| 起新线被拒（`ev_7_1`） | 报错只给两条出路，而第三条才是模型想要的 | **id 的合法用法住在契约里，模型只从包里拿到号** |
| leg64 的规则类别错位 | 去重后类别丢在败者身上 | **一条规则的身份不稳定（拿原文串当键）** |

⇒ 三件事长得完全不一样，**根是一条**：**"这个号在此时此地能不能这么用"没有单一权威**。

### 1.4 边界：这件事**不是**什么（防扩大化）

- ❌ **不是"看起来乱就整理"**（本仓最贵的错就是顺手重构，见 leg66 交接 §4.7 与 §3-C）。
- ❌ **不是引入依赖/构建步骤/TypeScript**：零依赖 + 无构建是**承重墙**（`test/browser-compat.test.js` 静态扫描整个浏览器面）。
- ❌ **不是重写引擎**：`settle.js` 的语义一个字不改，只改"顺序与不变量住在哪"。
- ❌ **不是动 `docs/`**（用户已拍板留仓）。
- ❌ **不是把文件按行数切开**（切法见 §3 丙，必须按语义边界）。

## 2. 甲案（★★★ 首选，正在出血的那一条）：引用完整性收成单一主人

### 2.1 病的一句话

**模型必须用 id 指东西，而"这个 id 现在能不能这么用"的规矩散在四处**：
包（给不给这个号）· 契约（形状允不允许）· 提示词（怎么教）· 结算复核（事后认不认）。
四处都能各自说话 ⇒ 任何一个"用错了格子"的引用，**要么被静默吞掉，要么被拒得莫名其妙**。

### 2.2 落地形状（三个模块的职责，不是三份复制品）

1. **`src/ref-rules.js`（新，叶子模块）**——**唯一的判据表**：每种引用（`newAgendas.source` /
   `entityUpdates.cause` / `newEntities.source` / `entityFates.source` / `newEvents.source`）
   × 每种源型（event/parent/state/ripple/plot/book/dialogueFact/entity/seed）
   ⇒ **合法 / 不合法 / 不合法且给哪条出路**。
   ★**它是纯数据 + 纯函数，零 import**（照 `params.js` 是叶子的先例）。
2. **`check-step.js` / `settle.js` / `pack.js` / `prompts.js` 全部改成"问它"**，
   ★**并立一条源码锁**：这四个文件里**不许再出现**各自手写的"因必须未闭环"这类判词
   （照 leg64 那条"分类只许住一处"的源码锁先例，`test/rule-kinds.test.js` 有样板）。
3. **报错文案从表里生成**：每条不合法都带**它自己的出路**（`ev_7_1` 那次的教训——
   出路漏了一条，模型就反复换号重试，每试一次白烧一轮）。

### 2.3 判据（可测，不是形容词）

- **M1**：给同一组引用喂四个消费口，**四个口的结论必须逐字一致**（喂 20 组真账样本 × 边角形状）。
- **M2**：**源码锁**——`check-step`/`settle`/`pack`/`prompts` 里不再有手写判词（正则扫，咬得住回潮）。
- **M3**：每一条"不合法"的报错**都含出路**（拿 leg66 那两条真账现场当夹具）。
- **M4**：**行为零变化**——`node --test` 901+ 全绿、冒烟 **8231 字节逐字节不变**（这是"只收口、不改语义"的证据）。

### 2.4 范围限制（本棒不做）

- ❌ 不放宽任何语义闸（"因必须未闭环""无源之物不存在"一个字不改）。
- ❌ 不新增源型（`ripple` 不进 `newAgendas`——leg66 §2.5 已论证：那是"线要挂在正在发生的事上"）。
- ❌ **不改包形状**（"在 closedRoots 那栏自带说明"是另一格，见 leg66 交接 §2.5 的登记项）：改包 = 改模型看到的东西 = 要单独拍板。

### 2.5 拍板点

1. 甲案**先做**（用户已说"优化项目结构"，但**"先做甲还是乙"要拍**）；
2. `ref-rules.js` 的形状（判据表 vs 一组谓词函数）；
3. 是否接受 **M4 的"行为零变化"**作为验收的第一条（我认为必须，否则分不清"收口"与"改语义"）。

## 3. 乙案与丙案

### 3.1 乙案（★★）：把"顺序承担语义"这件事显式化

**病**见 §1.2。**治法两条，选一条（拍板点）**：

- **乙-1（轻）**：在 `settleTick` 顶部写一张**顺序表**（一个数组常量：步骤名 + 一句话为什么在这个位置），
  并加一条判据锁住"表里的顺序 = 代码里的调用顺序"。
- **乙-2（重）**：把 `settleTick` 拆成**显式阶段**（每个阶段 `(world, ctx) → world`，纯函数形态），
  顺序由数组驱动。代价：动结算主链 = **高风险**，必须单独一棒、单独细案。

★**建议先乙-1**（低风险、立刻见效：下一任不用靠读 128 行去悟顺序）。

### 3.2 丙案（★）：两个大文件的切法——**按语义边界，不按行数**

| 文件 | 底数 | 切法（建议） | 风险 |
|---|---|---|---|
| `web/index.js` | 256 KB / **3689 行** | 按**动作总线**切：`bus` 的注册表 + 各自处理器分文件（`lookup-*` / `snapshot-*` / `chronicle-*` / `ents-*` / `param-*` / `init-*`），**保留一个薄接线层** | ★★ 高（浏览器侧，判据薄） |
| `src/render.js` | 195 KB / **2145 行** | 按**页签**切（八页各一文件 + 一个共享的 `escapeHtml`/词表模块），`renderAll` 留在薄壳 | ★★ 中高（`render.test.js` 206 KB 咬得很紧，是保护也是阻力） |

★**丙案的前置条件（硬）**：**先有甲案的收口**，否则切文件只会把"四处各说各话"切得更碎。
★**丙案的验收判据**：切完**渲染产物逐字节不变**（`renderAll` 对同一夹具的输出做哈希比对——
`test/render.test.js` 已有"同输入逐字节一致"的锁，直接复用）。
