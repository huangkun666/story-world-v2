## 0. 一句话

**同一个 JSON 里，`entities` 那一大段改成"表头 + 行式表格"（行内用 TAB 分列），
模型每轮少看约 9,517 token（整包 −49.3%），而信息一个比特都不少。**

## 1. 为什么是这里（实测：钱花在结构上，不是内容上）

真账 tick 17 真路径出包（`buildEvolutionPack(world, null)`，**真镜头 + 真 trimPack**）：

| 实测 | 值 | 说明 |
|---|---|---|
| 整包 | **57,917 字符 / est 19,306** | 预算 30,000 |
| `trimPack` | ★**没动刀**（`trimmed = null`） | 未超预算 |
| 镜头 | ★**618/618 行全进包，降级行 0** | `LENS_DEFAULT_MAX_TOKENS=30000` 未触发 |
| 实体段 | **18,683 est（96.8%）** | 其余九段合计 623 est |

**实体段的 56,047 个字符花在哪**（逐字符分类）：

| 项 | 字符 | 占比 |
|---|---|---|
| **键名**（`"kind":` 这类，**618 行各写一遍**） | **25,519** | **45.5%** |
| `id` 值（`e_bk_104`） | 6,068 | 10.8% |
| JSON 标点（`[]{}"",`） | 6,036 | 10.8% |
| **真内容·汉字** | **6,845** | **12.2%** |
| 真内容·非汉字 | 6,969 | 12.4% |

⇒ **约 67% 的字符是"键名 + 标点"这种纯结构开销**；真正的世界观内容只占 12%。
⇒ 这是 §7.4 那张表**没称重的一档**：它与"删字段"无关，是**纯表达法**。

## 2. 设计

### 2.1 只改"序列化"，不改"内部形状"（本细案的核心决定）

`prompts.js:70` 是唯一面向模型的出口，而它的输入是 `pack.text = JSON.stringify(pack)`。
⇒ **两条路**：

| | 甲·改内部形状（`pack.entities` 变成字符串数组） | ★**乙·只改序列化（推荐）** |
|---|---|---|
| `trimPack` | ★**连坐**：它往行里**删键**（`.slim`/`.idOnly`）⇒ 行变字符串后整段重写 | 零改动 |
| 面板 / 调试 | 连坐（读 `pack.entities[i].name`） | 零改动 |
| `lens.test.js:160` 等判据 | 连坐（断言 `Object.keys(row)`） | 零改动 |
| `JSON.parse(pack.text)` 往返 | 不再成立 | ★**仍成立**（换成一块字符串，仍是合法 JSON） |
| 改动点 | 5+ 处 | ★**1 处**（出包时加一个序列化器） |

**取乙案**：`pack.entities` 内部**仍是对象数组**（引擎、裁剪、面板、测试全部零扰动），
只在 `JSON.stringify` 时把这一格替换成行式文本块。

> 实现形状（供评审，非实施）：
> ```js
> const packText = (p) => JSON.stringify(p, (k, v) => (k === 'entities' ? entityBlock(v) : v));
> // estTokensOf 走**同一个** packText ⇒ 预算量体与实际发送量体永远同一口径（防"两把尺子"）
> ```
> ⚠ 已在写细案前核过一处易踩的坑：`JSON.stringify` 的 replacer **用返回值后的键**做键名匹配，
> 但 `trimPack` 的 `estTokensOf` 是**对整包量体**、`lensList` 的 `est` 是**对单行量体**——
> 单行调用（`JSON.stringify([id,name,kind])`）**不带 `entities` 键**，天然不受影响。

### 2.2 行式形状（一字一义、无转义需求）

```
entities:
id	kind	name	location	parent	实力	members
e_bk_104	character	白小娥	未明	散修	T1感气境
e_bk_7	faction	万法阁	东海浮空岛（推）				公输巧、唐锦绣、…、等10人
e_bk_6	faction	大虞	未明				沈天君、秦红袖、虞昭华
e_p1	character	你	未明
```

- **表头只写一次**（现状 618 行各写一遍键名 ⇒ 这是 §1 那 45.5% 的解毒剂）。
- **空值 = 空列**，**不用 `—` 充数**（沿用 leg30「没值的格子整个键不出现」的同一条规矩；硬规矩二「空着就是空着」）。
- ★**`locationNote`（`（推）`）并进 `location` 值**（`东海浮空岛（推）`）——现状它是**独立键**，
  行式下若单独成列会再添一列开销；并进去**信息零损失**（模型照样看得出这是结构推断而非书里明述）。
- **`members` 用 `、` 连接成单列**（现状是数组；`membersOf` 已含 `等N人`）⇒ **不需要转义**。

### 2.3 ★分隔符冲突实测（不是推理）

| 分隔符 | 618 行全部值（含 members 逐元素）命中 |
|---|---|
| `\t` TAB | **0** |
| `\|` 竖线 | **0** |
| `\n` | **0** |

⇒ 选 **TAB**，理由是它**不与内容冲突**且**最不易与内容混淆**（不用竖线是因为中文语境里 `|` 更可能在模型输出里出现）。
⚠ **但是**：这是**单本真账**的读数（泛用性铁律 §2 第 3 条）。故细案要求实施时**加一道出包期自检**（§5 判据 C），
而不是把"0 命中"当永久事实。

### 2.4 无损性核对（逐格还原）

按位置拆回、逐格比对：**3,231 个非空单元格全部一字不差**（含 142 个 `（推）` 标记、38 个成员名单）⇒ **零损失**。

## 3. 收益（三口径，防止"用错尺子"）

| 口径 | 现状 | 行式 | 省 |
|---|---|---|---|
| 字符 | 57,917 | 29,365 | 49.3% |
| **est（项目口径 字符/3）** | **19,306** | **9,789** | ★**9,517（49.3%）** |
| ★**下界**（汉字各 ≥1 token） | ≥24,339 | ≥12,479 | **≥11,860（49.6%）** |
| 上界（汉字 2 / ASCII 1） | 65,000 | 30,059 | 53.8% |

★**四档全落 49–54%** ⇒ **这个结论不依赖 tokenizer 选型**（也修正了 §7.4 那条"必须真 tokenizer 复量"的精度声明在**本结论上不必要**）。
★**行数不变**：模型看到的仍是 618 个实体（**视野一点没缩**），少的是结构开销。
⇒ 预算占用 **64% → 33%**，腾出的约 9.5k **正好可以给 Q1（世界变宽）后用**。

## 6. 风险与代价（如实记）

1. ★**冒烟 `8220 字节逐字节不变`这条基线会破**（它是"pack 文本没变"的锁，而本改动的**目的**就是改 pack 文本）。
   ⇒ 必须**先在副本上取前后对照**，把新终态字节记为 leg31 新基线（leg28 事故的教训：**"先证红"只走副本**）。
2. **模型可能读不懂空列**（`e_p1` 那行只有 4 列）。缓解：提示词写明"**缺列 = 空**"；
   且**保留全列对齐**（不采用"去尾空列"，虽然它多省 481 est ≈ 1.6 个百分点——**不拿可读性换这点钱**）。
3. **泛用性**：分隔符冲突是**单本**读数 ⇒ 判据 C 把它变成**出包期机械自检**（不靠"我看过没问题"）。
4. **不是"按需查"**：本改动**不减少行数、不减少字段**，纯表达法 ⇒ **不解决 Q1/Q2 的耦合**（§7）。
