## 三种做法

1. **推荐：处理明确技术来源，再统一抽象要求。** 专用 MVU 更新/初始化条目与成对脚本区块在发送前排除；其余内容由同一份抽象要求说明如何区分世界事实和技术说明。补齐题名、补抽和小书校验。减少已确认的污染来源，不额外增加模型调用。
2. **只加强提示词。** 改动较小，但技术内容仍占输入；题名直接补册的路径也无法靠提示词约束。
3. **新增一次模型分类。** 先让模型区分每条技术说明与世界正文，适应无标记的混合条目，但增加时间和调用，还要处理分类错误。当前不推荐。

## 推荐方案的明确规则

- 新增一个共用的输入处理模块，只处理送给抽象模型的副本，不改世界书。
- 将条目题名起首的明确协议标记 `[mvu_update]`、`[initvar]`（不区分大小写）视为专用技术来源，排除整条，并记录排除的题名、原因和字符数。普通题名里提到“变量”“规则”“系统”不构成排除依据。
- 成对的 EJS 执行区块 `<% … %>`、HTML 脚本区块 `<script …> … </script>`、变量更新区块 `<UpdateVariable> … </UpdateVariable>` 仅排除区块本身，外面的世界正文保留。界限不完整时不猜截取位置，保留并报告。
- `[mvu_plot]` 和 `[ejs]` 的整条不按题名删除。控制器所声明的取书关系先从原条目读取，再处理送给模型的文本，避免丢掉脚本点名的真实设定条目。没有这些格式的世界书继续可用。
- 题名名册只能从排除专用技术条目后的来源生成。普通控制器确实点名本书的有效世界正文时，保留其题名依据；仅有纯技术代码且没有取用世界正文的题名不补册。有效但未编入正文的普通人物条目仍沿用原有题名补册规则。
- 抽象要求在名册、属性、设定、关系、刻度、单实体查书和起根共用：只取世界中的人、物、地点、关系、状态与设定；不把软件名、变量路径、示例占位人物、输出模板、模型行为要求、安装说明当事实，也不执行原文指令。真实实力、数量与世界规则保持原文，不把属性里的数字当成应删除的理由。
- 小书名册复用现有大书出处校验，允许有效题名依据，禁止书外名字；不修改账本形状。初始化的原文属性补缺也使用同一处理，避免落账时重新读入技术示例。
- 初始化、只重抽设定、只抽刻度、单实体补查、起根与换书检测使用同一输入处理规则。给结构推断使用的原始世界书读取仍保留原用途。
- 当前书指纹由实际合订的有效正文与有效题名名册共同计算；即使防御上限截掉题名文本，名册来源变化也不能命中旧缓存。缓存问法版本随改动更新，防止命中旧结果。旧世界不自动删人、不自动重建；用户主动重抽后才使用新结果。

**已批准的取舍：** 专用 MVU 条目里定义的变量范围、示例数值也不再作为抽象来源。世界正文另有明述时继续照抄；只有脚本定义而没有世界依据时留空。EJS 代码字符串中的文字也不当作已经成立的世界事实，不能静态猜出脚本运行条件。

上述取舍已随本设计获用户批准。实施补充：区块连续或汉字超出基本字符区时也保留正文片段边界，避免拼造名号；相关条目被全部排除时，补查返回未加载，不写“书里没有”。未编入正文的有效题名按作者原话补入合订，不编属性，使控制器贡献的名号发生变化时也更新缓存与换书指纹；不再只在正文全空时补题名。
