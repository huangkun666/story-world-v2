## 3. 六条条款（全部"边界清晰、机械可核"）

> 筛选标准（用户 2026-09-12：「**我主要聚焦于边界清晰容易实现的功能**」）：
> 每条都必须能指出**账本上的哪一栏**，能写成判据，能红。**边界不清的已砍**（见 §3.7）。

### 3.1 新盘算：理由必须落在账上

- **现状**：`newAgendas[].source` 已要求 ∈ {event, parent, state} 且 ref 必须存在。
- **改**：`state` 源**不再无条件放行**——必须写明"为什么现在动"，且该理由**可核**：
  - `event` 源：ref 指向**未决**事件（非已闭环）；
  - `parent` 源：ref 指向**在飞**盘算（非已结算）；
  - `state` 源：必须带 `reason` 文本，且**所引处境的字段在账上真实存在**（如"某参数档位为某值"）。
- **落点**：`check-step.js` 新盘算段 · `prompts.js` 字段说明。
- **验收面**：N3 已实施（`agenda.source` 落账，leg29）⇒ **理由在账上可查**，这条才有判据可写。

### 3.2 新实体：形态判据 + 挂靠（**位置只记录、不判合法性**）

- **现状**：源必须 ∈ {book, event, dialogueFact} ⇒ **没人写过的人永远不能入场**。
- **改**：三条**形式判据**（不用词表、不用语义）：
  1. **有名字**：非空、非纯类型名（沿用 leg25 h 的黑名单口径）；
  2. **挂靠**：`parent` ∈ 在册势力，**或** 声明"由某在册实体牵出"（ref 必须存在）；
  3. ★**位置：只记录、不判合法性**（用户 ④ 定的）。
     - 账上 `location` **归一到集内项或 `未明`**（走既有 `normalizeToPositionSet`，零 token）；
     - **原话照抄进 `meta.entityFields`**（留痕、只呈现）；
     - ★**`newEntities[].location` 不再因"不在位置集"而丢弃这一条**（现状 `check-step.js:99` 会弃条）。
- **为什么不放开成"模型随便写地名"**：那会**替地图发明地方**。位置集不全（§4）是**已知的、接受的**限制，不是靠编坐标来补。
- **代价**：`ENTITIES` 持续增长（已有 `ENTITY_BIRTH_PER_TICK = 1` 兜着）。

### 3.3 加一个上限：**牵出次数**（防雪崩）

- **为什么必须有**：一个热门势力/人物可以无限牵人 ⇒ 复现 leg25 g 那种"一个入口放出上万条假关系"的形状。
- **形状**：每个在册实体**每 tick 能牵出几个**新实体 + 全局每 tick 上限（已有 `ENTITY_BIRTH_PER_TICK`）。
- **数字**：★**先出曲线再报批**（铁律 2），本文件不拍。

### 3.4 冲突检测（硬闸，必须恒 0）

| 不许 | 判据 |
|---|---|
| 引用**已 dead** 的实体当行动方 | `status !== 'dead'` |
| 把**已了结**的盘算当成"在办" | `agenda.closed !== true` |
| 写**玩家棋子**的行为/承诺 | `entity !== playerId`（红线 1 已有代码位） |
| 引用**不存在**的 ref | id 存在性（既有） |

### 3.5 发明物的永久性 + 标记

- **永久性**：发明物**即落账**，此后与真实体**同权**（能被盘算缠住、能被覆灭、能被引用）——"新"但不"轻"。
- **标记**：落 `meta.entityFields[id]` 一类留痕（沿用查书标记那套），标 `来源:'llm发明'`。
  - 理由：它是 §5 判据「**存活率**」的**唯一取数来源**；且**标记只是收据、不是二等公民**（与"同权"不冲突）。

### 3.6 提示词口径（契约层）

- 铁律 7 现写「**无源之物不存在**」⇒ 改「**发明要带出处与理由**」。
- ★**加一条给模型看的正向说明**：叙述（场景里编的细节）**不进账**；**事件、实体、盘算**必须落账且带因。
- ★**不加**"不许拿上一轮自己写的叙述当依据"——**账本上核不了**（叙述不是账目），只能靠嘴上说 ⇒ **边界不清，砍**（原 N5 的一部分，已砍）。

### 3.7 ★已砍的两条（记录在案，防止以后有人重新提）

## 6. 实体字段写回（`entityUpdates`）——**用户 ⑤ 定的方向**

### 6.1 形状（`world-step` 新增一节）

```json
entityUpdates: [
  { "entity": "<照抄输入 id>", "field": "<字段名>", "value": "<文本>",
    "cause": { "type": "event|agenda", "ref": "<上游 id>" }, "note": "为什么这次事件让它变了" }
]
```

★**这不是引入外部框架**：`world-step` + `check-step` **本身就是**酒馆 MVU 那套形状（模型输出结构化更新 → 框架校验 → 落存储）。缺的只是"实体字段"这一格。

### 6.2 五条约束（全机械可核）

| # | 约束 | 理由 |
|---|---|---|
| 1 | **`cause.ref` 必须在账上真实存在** | 「无源之物不存在」不放松——这是"因果变更"与"模型随口改"的**唯一分界** |
| 2 | **只许改现值**：不许改已落账的事件/编年 | 禁的是**改历史**，不是**改状态** |
| 3 | **`cause.ref` 指向的事件/盘算必须未闭环** | 防"拿三个月前一件旧事解释今天任何变化" |
| 4 | **玩家棋子 + 引擎 id 不可改** | 玩家的行为与承诺是**唯一真相源** |
| 5 | **`value` 是文本**，不许增量数值 | 四维浮点被删的原因（"用精确外壳装模糊内容"）；引擎**不换算、不进公式** |

**外加**：**每轮条数上限**（防一轮改 200 个实体 ⇒ 世界失去连续性）。★**数字先出曲线再报批**。

### 6.3 原话不会丢（零新增形状）

`fieldSource` 已存在（`ssot.schema.js:150`）⇒ 扩成 `{来源, 自哪一轮, 因哪件事, 原值}`。
模型读到的是：`实力：T8 破妄（原话 T9渡劫巅峰，第 12 轮那场血战后）` ⇒ **原话与现值同时在场、且能追到账**。

### 6.4 死亡与复活（**比"字段可写"重**：它改变"谁能出场"）

现状**三处 + 一处过滤**一起锁着"死亡不可逆"：

| 落点 | 现在 | 改 |
|---|---|---|
| `ssot.schema.js:135` | `dead=终局不复归` | `dead=可被带因复活`（枚举值不变） |
| `check-step.js:106` | 已覆灭者不许再提覆灭 | 照旧（防重复覆灭），**新增"复活提案"通道**：`dead → active/retired` 且**必须带 cause** |
| `settle.js:624/643` | 落 dead = 终局 | 允许带因改回 |
| ★**`pack.js:51`** | **dead/retired 从演化上下文里滤掉** | ★**必须一并改**——否则"复活了但模型看不见他"，世界继续当他死了 |

⚠**风险**：复活改变"谁能出场"的面 ⇒ 要防"死而复生循环"（模型每轮复活一个人刷存在感）。
**建议**：**复活与覆灭共享同一份每轮预算**，且 `cause` 指向的事件**本身必须是"复活/重生"性质**（不能拿无关的事当理由）。

### 6.5 这个选择的真实代价（必须记在案）

**引擎从此放弃"这值对不对"的判断权**，只保留"这变更有因、有痕、有额度"的核验。
⇒ 50 轮后可能出现"同一人实力变了三次、前后不一致"，**引擎一律照收**——因为**不能裁胜负、不能打分、不能判对错**（承重墙）。
**补救是留痕，不是判断**：每条变更**永久落账**（值 + 因 + 轮次）⇒ "前后矛盾"**可被发现**，但**引擎不替世界仲裁**。这正是"**账房 + 史官**"的本分。

### 7.2 三级字段表（提案）

| 级 | 字段 | 什么时候进包 |
|---|---|---|
| **甲·每轮必带** | `id` · `name` · `kind` · `status` · 在飞盘算/未决事件的关联 | 每轮 |

| **丙·用时再查** | `身份` · `定位` · `性质` · `规模` · `倾向` · `organs` · `branches` · 以及**所有 `entityUpdates` 新写的字段** | 默认不进包 |

### 7.3 ★「用时再查」的三种实现——**只有第三种真省 token**

| 实现 | 省 token | 代价 |
|---|---|---|
| 查询结果**拼进包** | ❌ 不省（等于"按需变成每轮带"） | —— |
| 查询要**额外一次模型调用**（像现有查书那条路） | ✅ 省 | **每次查询本身烧 token + 引入噪声**（用户已提出这个担忧） |
| ★**模型主动检索**（给模型一个查询入口，它自己要） | ✅ 省，最灵活 | **项目现在没有这个面**：`entityFields` 那条路是**引擎选人后去查**，不是模型自己查 ⇒ **新增接线** |

**用户已拍板：要给模型主动查的接口。** ⇒ 待定项：**接口形状 / 每次查询预算 / 查询失败如何回话 / 与 `entityFields` 现有查书路径的关系**（§8 Q2）。

### 7.4 零信息损失的表达优化（收益最大，且与内容无关）

| # | 动作 | 省 | 风险 |
|---|---|---|---|
| **①** | **`id` 改短号**（`e_bk_104` → `e104` / 序号；进出双向映射） | ~3,000 | `check-step` 要先把短号映回真 id；映射错了 = 事故 |
