## 3. 小说家条款细案（`docs/spec-novelist-clause.md`，**待拍板**）+ N3 已实施

**用户原话**：「如果我们给 ai 自由创作权呢？给 llm 小说家的身法？**当然聊天提取到的内容是不能创作的**」。

**全篇的骨＝认知更正**：把项目一路在禁的"编造事实"**拆成三件不同性质的事**：

| | 例 | 该不该禁 |
|---|---|---|
| ① **编数**（把编的冒充算的） | 四维浮点 兵力 0.6 | **继续禁**（已删，对的） |
| ② **编故事**（叙述内容） | "城外的流民开始聚集" | ★**该放开**——模型本来就是"笔" |
| ③ **改写已确立的事实** | 玩家说过的话、书里写死的设定 | ★**绝对禁**（用户那句话正是此条） |

现状把 ② 也一起禁了（`prompts.js` 铁律 7「无源之物不存在」+ 三条来源闸）⇒
**一支只能推进已有的事、不能写出新的事的笔 ⇒ 世界自己长不出第二个源头**。

**设计**＝**来源闸 → 一致性闸**（机械可核的那半一条不放松）；三候选 **A**（只放开动机）/ **B 推荐**（A + 入局按"挂靠"放开）/
**C**（B + 事件位置放开 `未明`）；五条双面约束；八条判据（**因果面宽度**为唯一"成了"信号 + 一致性违规必须恒 0）。

**★写细案时给自己派了两次证伪，其中一次推翻我自己的假设**：
- **上游复用度实测最大 = 1**（7 个被引为上游的事件每个只被引一次）⇒ 原拟的"来源多样性上限 N"**是纸面机制、建议删除**，
  改判据为**"独立链头数"**（13 条事只来自 **6 个独立开头**）。
- ★**更硬的一条**：`ssot.schema.js` 的 agenda 是 **`additional: false`** 且**没有 `source` 字段**，
  `settle.js` 只落 `if (na.source.type === 'parent') agenda.parentId = ...` ⇒
  **event 源与 state 源在出生那一刻被丢掉**，真账四条盘算 `parentId` 全 null ⇒ **引擎事后说不清一条盘算怎么来的**。

**★N3 已实施**（用户令「先做 N3」）：schema 增**可选** `source: {type, ref?}`（与 world-step 同枚举；**可选 ⇒ 旧账零扰动**）；

## 4. 记忆投递：5 处真缺陷 + 表形状对齐（用户实机三轮反馈逼出）

### 4.1 修掉的 5 处真缺陷（都有判据）

| # | 病 | 治法 |
|---|---|---|
| 1 | **状态表每轮换一个新 id**（`sw2_state_<tick>`），插件按 id 合并 ⇒ **每轮新增一条**（真账实测三条并存），与本表"一表一条覆盖"的契约自相矛盾 | 改**固定 id `sw2_state`** |
| 2 | **旧记录永远清不掉**（只并合、从不清理） | 落盘后**只清我方 `sw2_` 前缀**里"本次没投"的记录；**非此前缀一个字不动**（leg27 g 的教训） |
| 3 | **旧表定义没清** ⇒ 三张自定义表永远赖在侧栏（**这正是用户问的"多出三个来"**） | 写入时删 `LEGACY_TABLE_IDS` 三个 id 的表定义与记录键 |
| 4 | 闭档那支**先切后滤**（脏数据白占预算） | 改"**先滤后切**"，与同函数在飞档的口径对齐 |
| 5 | ★**同 id 表定义"已存在就跳过"** ⇒ 插件本就带 `world_setting`/`item_tracking`，**我们给的列与表名一个字都进不去**（"改了个寂寞"） | 改**同 id 覆盖** |

★另有**我自己犯的两处**，都被既有判据当场抓住：**`pushToMemory` 回传轮次仍读已删的 `轮次` 键**（自证面会报空轮）；
**把轮次拼进事件标题**致"空标题不投"闸失效（`"   "` 拼上就不空了）。

### 4.2 表形状对齐（用户拍板「对齐插件内置表形状」）

插件 `ui/memory-window.js:3777` 的 `createTableWorkspaceView` **按 `table.id` 硬编码**：只认五个内置 id，
其余一律 `return empty`（空 div）⇒ **自定义表的详情页永远空白**。★**实测后收窄的口径**：
五个内置表里**只有三个**是"每条记录一张卡＋有详情"（`character_profile`/`item_tracking`/`world_setting`），
且 `character_profile` **被用户自己的「角色档案」占着** ⇒ **我们只有两个槽位**；
另两个（`plot_summary`/`memory_summary`）是**单例表**（拿它们装"一次事件一行"会**从 14 条变两条**，更糟）。

| 逻辑表 | 落到插件的表 | 列 |
|---|---|---|
| 世界状态（一表一条） | `world_setting` | 设定名 / 类型 / 详细说明 |
| 史卷纪要（每条一段） | `world_setting`（**同表兄弟记录**，id 前缀 `sw2_ms_`） | 同上 |
| 世界大事（每条一次） | `item_tracking` | 物品名称 / 物品描述 / 物品位置 / 轮次 |

### 4.3 "看不到内容"的真根因：**三层缓存**（本棒最贵的一课）

现象**一模一样**（界面毫无变化），根因**三次完全不同**：

| # | 根因 | 怎么验出来的 |
|---|---|---|
| ① | **浏览器缓存的旧 ES 模块**（代码压根没跑） | 盘上 `saveOrigin=auto`、旧列名；动态 `import` 连新导出都拿不到 |
| ② | **旧表定义没清**（我漏做的一半） | Node 端到端复演抓到 |
| ③ | **插件内存缓存**（我们绕过它的 UI 写存储，它不知道 ⇒ 用它自己的旧状态回写，把表名盖回去） | 自检行全绿 + 读插件源码找到它自己的通道 |

⇒ **"代码已在盘上" ≠ "浏览器在跑它" ≠ "插件看得到"**，必须**分开验**，且验的手段要是**判据**
（部署位哈希比对 / 投递后自检行 / 事件派发锁），不能靠"重刷一下试试"。
新增只读自检 `memoryStoreReport()` / `memoryStoreCheckLine()`（**随每次投递打一行**）与实际留痕。

**插件自己的两条通道**：`window.addEventListener('yzm-memory-state-updated', reloadStateFromStorage)`（叫它重读+重绘）；
本棒在落盘后**派发该事件（立即 + 600ms 各一次）**，并在 **700ms 做一次只改表名、不动记录**的**幂等校正**。

### 4.4 三条追问的实测答复（下一棒别再重复调研）

1. **「每次开新聊天都要自己改吗？」→ 不用**：vm 里跑插件真存储代码实测——新聊天 `loadState` 拿到插件**自带的 5 张默认表**，
   我们第一次投递**自己带上表定义** ⇒ 新聊天里名字与列**都是我们的**。只有**当前这个老聊天**因插件内存里存着旧名字才需校正。
2. **「为什么不能自己建表？」→ 能建，但没用**：插件支持自定义表（能存、能列出），但**只为五个内置 id 写了渲染器**
   ⇒ 自定义 id 的**详情页永远空白**（正是"看不到内容"的病根）。
3. **「为什么把地图放进去了」→ 我理解错了需求，已删**：位置与设定本来就在世界设定里、聊天 LLM 看得到，
   记忆该记的是"**世界发生了什么**" ⇒ 状态表**四列改三列**（设定名/类型/详细说明），只留在办之事/未了结之事/参数；
   `positionLine` 的 import 一并删除（死 import 同死代码）。
