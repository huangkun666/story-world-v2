## 5. ★★ 用户提的架构方向（**讨论到接口级，未实施**）

用户原话（三段）：①「**能不能让聊天模型输出这一轮各个角色的原子行动然后用标签包裹之后直接用正则提取送给插件模型从而避免冲突**」
②「插件根本不需要维护主角的属性因为根本就不规划主角，而根据聊天模型得来的各个角色的原子行动告诉插件模型后，插件模型也不需要再去模拟本轮的这些角色」
③「**我认为可以在发送消息前对聊天llm进行上下文注入**」

**核过的现状（这是本方案的全部前提）**：

| 方向 | 现状 |
|---|---|
| 聊天模型 → 世界引擎 | **没有通路**（不读 chat；`.advance()` 不传对话） |
| 世界引擎 → 聊天模型 | **也没有通路**：`renderStreams().injection`（`【世界动向】`/`【你的行迹】`）**没有任何生产消费者**；唯一的投递是 yuuki-Memory 插件（`memory-bridge.js`，要 `memoryEnabled` 开关），投的是**表格记录**不是聊天上下文 |
| prompt 注入面 | ★**零**：全仓没有 `setExtensionPrompt` / `worldInfo` 写入 / prompt pipeline 钩子（只挂了 2 个事件钩子） |

**用户第 ③ 条是对的，接口是现成的**：ST 的 [`setExtensionPrompt`](https://docs.sillytavern.app/for_contributors/writing-extensions.md)
（名/内容/位置/深度/角色/每轮扫）就是"发送消息前塞进上下文"；
事件名 [`CHAT_COMPLETION_PROMPT_READY`（chat completion 路）/ `GENERATE_AFTER_COMBINE_PROMPTS`（text completion 路）](https://deepwiki.com/SillyTavern/SillyTavern/2.3-event-system-and-module-communication#1)。

**定稿形态（本棒推演出的四条纪律，供下一任直接接）**：

1. **标签只喂两样，不当世界步**：①落子事实（补上现在恒空的那一格）②**点名名单**（喂 `gate.js:43` 的 `named` 集——
   现在那里只有 `moveFact.object` 一条）。真正的世界步仍由引擎出 ⇒ 聊天模型**不获得写账权限**（红线不破），
   但它的叙事**真的影响引擎**（点名才有资格立线，正是 `prompts.js:212-214` 那条机制）。
2. **玩家不许出现在标签的主语位**（只能当宾语）⇒ "谁演谁"变成**结构性**的，不靠提示词自觉。
3. **id 归属是唯一的实质难点**：标签里是名字，`actions[].entity` 要 id（`prompts.js:290` 写死"照抄输入"）
   ⇒ 必须钉"主语只能是注入名单里出现过的名号"+ 走 `aliases` 归一。**注入面因此必须把名牌递进聊天上下文**
   （`pack.js` 已有这份料：`entities` 段 + `aliases`）——★**工作量在这儿，不在正则**。
4. **两个坑**：①**别变成同一件事记两遍**（引擎提示词要加"标签里点过名的角色，这一步不要再替它出手"）；
   ②**时差一格是设计决定的**（`streams.js:75`「落子已记，兑现待棋局结算（时差 §4.7）」）——
   要消掉只能让叙事模型预测世界反应，那是编数、是红线。

**唯一实质风险（要跟用户讲清再动手）**：这会把插件从**纯面板插件**变成**改用户聊天上下文的东西**；
注入的"世界状态"会让剧情越来越围着账本转（**叙事被账本殖民**）⇒ 注入该**分两段、可分别关**
（只给名号对照 = 最小必要 / 再给世界动向 = 会引导剧情，默认关），且每轮注入量要记账。
