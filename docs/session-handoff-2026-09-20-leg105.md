## 1. ★★★ 诊断全程（下一任接手 UI 报障时照这条方法论走）

### 1.1 先排查错的那一层（不是白干）

用户第一句「点了下一页没反应（有 5 页）」先按**实体页**分页器查：`renderEntsPager`/`selectEntityPage`/
`turnEntsPage`/`bus['ents-page']` 唯一派发点/`dispatchAction`+`__sw2Actions`/`refreshSections` 无早退/
`bindActions` 时序/无 pointer 拦截——**全链无罪**，并做了 Node 探针实证（246 实体翻页正确渲染）。
★用户随后截屏指认真凶在**编年页**：命中 246 = 「账目 246」chip 的口径，账目层用的是**另一个游标 `pageBook`**。
★**这一段的意义**：排查错层不是浪费——「实体层无罪」的结论拦住了后面所有人在那条链上继续挖。

### 1.2 ★ 真凶：双重死控件（两处都查实了）

- **①渲染侧**：细案 §3.1 定「账目组**全量给出去（不分页）**」⇒ `bookGroups` 四组永远画全量账行，
  而分页器切的 `sel.books.rows`（本页 60 条）**根本没人消费**——页码翻到天上去，行一条不动。
- **②接线侧**：`web/index.js` 的 `dispatchAction` click 委托组装 payload 的白名单里**没有 `data-layer`**
  ⇒ `bus['ch-page']` 收到 `layer=undefined`、兜底成 `'event'` ⇒ 点了**永远在翻事件层的游标**
  ⇒ **这层的页码连"跳"都不会跳**——这正是用户看到的全部现象（「翻页页数也不会跳」）。
- ★★为什么删不修：账目层四个子组**默认全收起**。就算把两处都修好，得到的仍是细案 §3.4 自己
  点名不许交付的那个反模式——「**玩家看见『第 1 / 5 页』却在一块收起的名单上翻页**」。
  **细案当初预言了病、却把豁免漏给了正好长病的那一层**。

### 1.3 为什么不修还有一条工程理由

修法要给 `bookGroups` 换口径（四组改吃本页 60 条），会动 `test/chronicle-page.test.js` 里**五条判据**
（子类合计=总行数那条底线、真账 70/92/50/29 那条全量读数……）——为一个用户明确说没用的控件，
付"五条判据重标定"的代价，不值。**删的成本≈0**。

## 3. ★ 病根那一刀（`web/index.js` **一行**）

