## 2. 交付：两刀 ＋ 一次发布（已提交、已上线）

### 2.1 病（一句话）

**世界书作者写 `{{user}}` 是惯例**（那是"玩家"的占位符）。**酒馆自己会在组装提示词时把它换成
人设名——但那是酒馆的活儿**；我们**绕过了酒馆、直接读条目原文**（`src/init-source.js` 的
`normalizeEntry`），于是那个宏**原封不动**进了抽取。模型看见书里有个叫 `{{user}}` 的人，
**忠实地把它抽成了角色**——**它不是乱编，是照抄我们递过去的原文**。

★**后果**：账上变成"两个你"。而**认领棋子那把尺子只比名字相不相等**（`web/index.js` 的
`namePlayerPiece`：`e.name === nm`）⇒「{{user}}」与「怪璃」**永远不相等** ⇒ 认领不了 ⇒
那枚实体留在账上**当棋手** ⇒ 世界模型每轮**同时看到两枚棋子**
（与用户当年那句「**又把主角演了**」同一个形状——leg32h 修过一次）。

## 4. ★★★ 本笔最值钱的四条

### ① **"模型想单独抽主角"这个直觉方向反了——宏是"另一个名字"，不是"同一个人的第二份"**

用户猜「**是不是因为模型想要单独抽象出主角才搞的**」。**不是。**
**主角是引擎自己在【开始新世界】那一刻安好的**（`attachPlayerPiece`，名字取酒馆人设名 `name1`），
**模型没有理由再抽一个**。模型看到的是：**棋子的名字（怪璃）≠ 书里的那个名字（`{{user}}`）**
⇒ 它眼里这**是两个人** ⇒ 它忠实地把 `{{user}}` 也抽了。

⇒ ★**教训**：**用户给的解释对不对，要用代码去验，不能顺着答**。他这一猜若被追认，
就会去改"主角认领"那条路——**而病在"送进去的原文"那一头**，改认领一处都不治。

### ② **"宏 vs 名字"是一次真实的碰撞：酒馆的宏在我们读原文那一刻没有解析器**

这不是"我们写错了"，是**两个系统的边界**：酒馆在**组装提示词**时才替换宏，
而**我们绕过了那一步、直接读条目**（这是我们**故意**做的——为了拿到作者的原稿，见 `src/init-source.js` 头注）。
⇒ ★**教训**：**凡是"我们绕过了宿主直接读原文"的地方，都要问一句"宿主在这段文本上还做过什么"**
（宏替换／变量展开／格式清洗）。这一族 bug 的形状是**"转发原文"顺手把宿主的语义丢掉了**。

### ③ **紧急修的两条纪律：先定根因、再动手；读不到真账就不猜**

- 用户报的是**社区用户**的 bug ⇒ **那份真账在别人机器上，我读不到**。
  我没有"照现象猜一个改法"，而是**从代码机制定根因**：全仓搜 `{{user}}` ＝ 0 处 ⇒
  **这是机制，与哪台机器无关**（凡是书里有这个宏的都会中）。
- ★**唯一读不到的那一格**（那位用户的 `name1` 到底是真名还是字面量）**不影响结论**——
  两种情形的修法是同一条（能换就换、读不到就挡）。

⇒ ★**教训**：**"读不到证据"不等于"不能定案"**——只要病是**机制**（不是某个数据），
就能用代码把它钉死。反过来，**别拿"某个用户的账"去证明机制**（那是二等证据）。

### ④ **一次"顶破硬锁"的临场：搬一族出去，不抬锁**

第一版把机制代码直接写进 `web/index.js` ⇒ **3166 行，顶破 3100 硬锁** ⇒ 三条判据当场红。
照本仓既有做法：**整族搬进新家 `web/world-entity-migration.js`，不抬锁**（`STATE.md` 里那句

### 9.5 ★★ 本场澄清的一条设计口径：**仓里有两片"森林"，记忆只用其中一片**

用户问设计时的原话：「**已知我们的插件里的对象是一整个森林，之前还做了一个故事线切分，就是按树来切分**」。
★**方向对，但那句话里其实是两片森林**：

| | 是哪片森林 | 代码里长什么样 | 记忆引擎拿它当什么 |
|---|---|---|---|
| **甲** | **势力／角色的树** | `parent`／`branches`／`organs`（势力→上级、角色→所属、子势力、机构） | ★**只当"名字"用**（检索的钥匙） |
| **乙** | ★**因果的森林** | 事件 ＋ 盘算，**单亲**（`source` 永远一条）⇒ 天然互不相交 | ★**这才是记忆的唯一切割轴** |

★★**为什么必须按"乙"切、不能按"甲"切**（一个具体例子，这是本场讨论的核心）：

```
万法阁商队集结(第12轮) → 借道 → 遭遇伏击 → 求援 → 邻国介入 → 商队覆灭(第73轮)
```
它横跨 **3 个势力、2 个国家、61 轮**：
- **按势力树切** ⇒ 商队那段归万法阁、伏击那段归山贼、求援那段归邻国 ⇒ **一条完整的故事被切成三段**；
- **按因果切** ⇒ 它**本来就是一条线** ⇒ 一头一尾清清楚楚。

⇒ ★**一句话**：**一棵势力树不是一段故事；一段故事是一条因果线，它横跨好多个势力。**
**势力树是"检索的钥匙"，不是"切割的轴"。**

### 9.7 ★★★ 本场量出来的两条"卷的现读"（回应"检索成不成问题"）

用户当场问：「**卷是放在本地卷库，那么检索是不成问题的吧？**」⇒ ★**走通了整条链，答案：通路是完整的，但有两处代价**。

**① 通路是完整的（不是"少一半"）**：

```
web/index.js:1604   ledgerVolumes()          ← 同步取"当前聊天的全部卷（含 rows）"
      ↓
src/tick.js:298     buildEvolutionPack(..., { volumes: ledgerVolumes })
      ↓
src/pack.js:1449    fetchChroniclePast(ssot, volumes)   ← 「纪事」那一栏
src/pack.js:1129    fetchRelatedPast(..., { volumes })  ← 「相关往事」那一栏
      ↓
src/ledger-recall.js:145  chronicleOf(ssot, volumes)    ← 卷行并进热账行，合成一条时间线
```
★**这件事不是天生的**：leg119 之前每一路取法都**只读热账**，实测编年 360 行轮转后 **186 行当场取不回来**
（其中 **119 条是真往事**）、「纪事」栏 **237 → 118 条**。那一笔专门补的就是这一条，**有判据钉着**。

**② 两处真代价**：
- ★**读卷是"整库全读再筛"**：`web/idb-backend.js:55` 那一句是 `s.getAll()`（**不加条件**），
  取回来再在 JS 里按 `${chatId}:` 前缀筛 ⇒ **卷库里"所有聊天、所有卷"的整份内容进一次内存**。
  ⇒ 卷数从几十涨到几千，单次读的量同比例涨（**而"一轮一卷"正是在制造这个**）。
- ★**一轮读一次，不是每次都读**：`ledgerVolumes()` 是**同步**函数，直接返回内存缓存、顺手后台刷一次
  ⇒ **面板重绘、状态条刷新都不碰卷库**。碎卷的问题是"每推进一步读一次整库"，不是"卡在界面上"。

**③ 一条要如实说的脆弱处**：IndexedDB 是**浏览器本地**的。热账（`chat_metadata`）随聊天文件走，
**卷不随** ⇒ 换浏览器／清站点数据／在另一台机器打开同一个聊天，**那一段往事检索不到**
（导出/导入那条路是带着卷的）。★碎片化不影响这一条，但它是个前提。
