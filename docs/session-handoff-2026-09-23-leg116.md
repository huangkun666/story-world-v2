## 1. 病：排序在"卡预算"的时候就是决定性的

### 1.1 人话版

取往事分两步：**① 先把沾边的都捞出来；② 按字符预算切一刀**（第四段给聊天模型的额度是 1600 字）。
★**第二刀是"谁排前面谁留下"**——所以**排序直接决定模型看到什么**。

而 leg115 那版里：**按账上真名取（第四段的主路）一条排序都没有**，按编年表的原始顺序返回
（账只往后加 ⇒ **老的在前**）⇒ 1600 字里装的是**最老的**那些往事。
**按词取（兜底路）反倒有排序**（代码里写着"命中多的在前、同分按轮次新的在前"）⇒ 装的是**最新的**。
⇒ 两条路一个记着陈年旧账、一个记着刚发生的事，**口径互相打架**。

### 1.2 ★实测（只读探针 · 200 行账 · 每行都点得到"黄坤"）

| 取法 | 修之前留下的轮次 | 修之后 |
|---|---|---|
| **按名取**（主路） | **1 → 64**（最老的 64 行） | **38 → 100** ✅ |
| **按词取**（兜底） | 38 → 100 | 38 → 100 ✅ |
| 照因果上溯（有向） | ev_3 → ev_2 → ev_1 | **不动**（链顺序是信息） |

★探针**只读**：真模块、真 API、造一份 200 行的账；跑完删掉，仓里一个字节没碰。

### 1.3 为什么这不是"风格问题"

读者是**写下一段正文的模型**。它要知道"刚刚发生了什么"才接得上；把最老的往事摆在它眼前，
等于每一轮都先给它讲一遍开天辟地——**时间印记没写错（轮次都标着），错的是摆上去的那一批**。

## 3. ★两个旋钮为什么是"装饰"（撤掉的依据，不是嫌它丑）

| 旋钮 | 实测 | 结论 |
|---|---|---|
| `sources`（"取哪些源"五选：编年/事件/里程碑/盘算/实体） | 同 `modes`、只改 `sources` 取三种值（`[chronicle]` / `[events]` / `[]`）⇒ **取到的行 id 逐个相同** | **没有任何一个 mode 读它**——每种方式只读一种源，这旋钮改不动结果。唯一真管事的源闸是 `includeArchive`（里程碑那道） |
| `limit` | 只有 `recent` 读它；`names`/`keyword`/`entity`/`id`/`tick`/`cause` **一律不读** | 而 `inject.js` 正传着 `turns * 6` ⇒ **让人以为 `turns` 是个能调的旋钮，实际只有 `maxChars` 在管事** |

⇒ 这与本仓那条血证同源：**没有消费方的抽象 = 死抽屉**（先例 `trimPack` 在生产里 0 调用）。
leg115 已经因为死抽屉被用户问穿过一次（交接 §2.5），**这一处是同一件事的残余**：长在**接口内部**。
★哪天真要"只要某一种源"，正确做法是**加一种方式**（方式才是取数的真正决定者），不是加一层筛子。
